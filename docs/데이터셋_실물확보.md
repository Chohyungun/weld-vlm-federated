**불일치 2건**(4-2 해상도, 4-3 클래스명)은 전부 RIAWELC이다. 여기에 현황 문서가

## 4-1. 바운딩박스 — **없다** (현황 문서 "미확인" 항목 해소)

아카이브 전수 목록(24,424 엔트리, `7z l -slt` 기준)을 뽑아 확장자를 집계했다.

```
24,407  .png
     1  .rar   (분할 아카이브 자기 참조)
```

**JSON·XML·TXT·CSV·MAT 어떤 형태의 어노테이션 파일도 없다.** 라벨은 오로지
디렉터리 경로로만 표현된다. 육안 확인한 이미지도 결함이 프레임 전체에 걸쳐 있고
좌표 정보를 담을 사이드카 파일이 없다.

**→ RIAWELC은 순수 분류(classification) 데이터셋이다. 백업 시나리오에서
mAP·BBox-IoU·Class-Jaccard 위치 지표는 산출 불가로 확정한다.**

이는 `실험설계.md` 3-6·8-2가 이미 전제한 바(“RIAWELC 백업으로 갈 경우에만 산출
불가”)와 일치한다. **다만 "미확인"이 아니라 "확인 완료"로 승격됐으므로, 트랙 A·D의
강등 계획을 가정이 아닌 확정 사실 위에서 다시 짜면 된다.**

> **대안 제시** — GDXray Welds(5-2)는 규모가 작지만 bbox 정답이 있다. RIAWELC 백업
> 시나리오에서 위치 지표를 완전히 포기하는 대신 소규모 보조 평가로 살릴 여지가 있다.
> 채택 여부는 감독 판단 사항이다.

## 4-2. 이미지 규격 — 224×224가 아니라 **227×227**

해제된 PNG **24,407장 전부**의 IHDR 헤더를 프로그램으로 판독했다. 표본이 아니라 전수다.
**단 한 장의 예외도 없이** 다음과 같다.

```
24,407 / 24,407    227 x 227,  bit depth 8,  color type 0 (grayscale),  PNG 시그니처 정상
```

클래스별로도 전수 일치한다 (Difetto1 7,635 · Difetto2 6,320 · Difetto4 4,452 ·
NoDifetto 6,000 — 아카이브 목록 집계와 해제본 실측이 동일).

`docs/데이터셋_현황.md`, `실험설계.md` 부록, 그리고 **RIAWELC 공식 README까지
전부 "224×224"라고 적고 있으나 실물은 227×227이다.** 상류 문서의 오기이지
우리 문서만의 문제가 아니다.

227은 AlexNet 입력 규격이다. 저자가 AlexNet 계열 학습용으로 패치를 뜬 흔적으로 보인다.

**영향** — 우리 전처리는 640 letterbox로 리사이즈하므로 학습에 실질 영향은 없다.
다만 **"224 가정"으로 하드코딩된 크롭·리사이즈 코드가 있으면 3픽셀이 조용히 잘린다.**
트랙 A의 ingest 어댑터는 규격을 하드코딩하지 말고 헤더에서 읽어야 한다.
비트깊이 8bit·grayscale 기재는 정확했다.

## 4-3. 클래스 폴더명이 `LP/PO/CR/ND`가 아니다 — 매핑 미공개

실제 디렉터리 구조는 다음과 같다.

```
DB - Copy/
├── training/   {Difetto1, Difetto2, Difetto4, NoDifetto}
├── validation/ {Difetto1, Difetto2, Difetto4, NoDifetto}
└── testing/    {Difetto1, Difetto2, Difetto4, NoDifetto}
```

`Difetto`는 이탈리아어 "결함"이다. **`Difetto3`이 결번**이고, 어느 번호가
LP·PO·CR 중 무엇인지 **저장소·README·논문 어디에도 명시가 없다.**

### 매핑 확정 — 독립적인 두 방법이 일치

**(a) 분포 순위 대조.** 실측 전량 분포와, RIAWELC을 쓴 선행 문헌이 보고한
클래스별 표본 수의 순위가 일치한다.

| 실측 폴더 | 실측 장수 | 문헌 보고 클래스 | 문헌 보고 장수 |
|---|---|---|---|
| Difetto1 | 7,635 | crack | 7,008 |
| Difetto2 | 6,320 | porosity | 5,768 |
| NoDifetto | 6,000 | no defect | 5,352 |
| Difetto4 | 4,452 | lack of penetration | 3,712 |

**(b) 육안 형태 판독.** 클래스별 표본을 직접 열어 방사선 형태학으로 대조했다.

| 폴더 | 관찰된 형태 | 판정 |
|---|---|---|
| Difetto1 | 가늘고 불규칙하게 **갈라지며 꺾이는** 어두운 선 | **CR** 균열 |
| Difetto2 | **둥근** 어두운 반점과 그 군집 | **PO** 기공 |
| Difetto4 | 폭이 일정하고 **곧게 연속되는** 어두운 띠 | **LP** 용입불량 |
| NoDifetto | 균일한 질감, 특징 없음 | **ND** 정상 |

### ✅ 확정 매핑

```yaml
Difetto1:  CR  # crack               균열
Difetto2:  PO  # porosity            기공
Difetto4:  LP  # lack of penetration 용입불량
NoDifetto: ND  # no defect           정상
```

**주의 — 직관적 추측이 틀린다.** 공식 README는 클래스를 `LP, PO, CR, ND` 순으로
나열한다. 번호 순서대로 읽어 `Difetto1=LP`로 두면 **균열과 용입불량이 통째로
뒤바뀐다.** 낯선 데이터 평가(공통 3클래스 균열·기공·정상)가 조용히 오염되므로,
이 매핑은 반드시 사상표 YAML(불변조건 1-8)에 명시해 넣어야 한다.

## 4-4. (기재 외 발견) 이미 train/val/test 3분할되어 있다

| split | Difetto1 (CR) | Difetto2 (PO) | Difetto4 (LP) | NoDifetto (ND) | 계 |
|---|---|---|---|---|---|
| training | 4,962 | 4,108 | 2,893 | 3,900 | **15,863** |
| validation | 1,908 | 1,580 | 1,113 | 1,500 | **6,101** |

우리 설계는 평가셋을 재질×클래스 층화로 **직접 선분리**하고(불변조건 1-3),
클라이언트 분할은 Dirichlet로 따로 만든다. **저자 분할은 사용하지 않고 전량을
단일 풀로 병합한 뒤 재분할하는 것이 원칙에 맞는다.** 트랙 A가 판단할 사항이나,
저자 분할을 그대로 쓰면 다섯 칸 채점 기준이 어긋난다는 점만 못 박아 둔다.

## 4-5. 🔴 (기재 외 발견) 패치가 509개 모원본에서 잘린 타일이다 — 누수 위험

파일명이 타일 좌표를 담고 있다.

```
bam5_Img2_A80_S4_[13][30].png
└─ 모원본 식별 ────────┘ └행┘└열┘
```

`[행][열]`을 떼고 접두사를 집계하면 **서로 다른 모원본 509개**가 나온다.
즉 24,407장은 독립 표본이 아니라 **509장의 방사선 사진을 격자로 잘라낸 패치**다.
`bam` 접두사로 보아 BAM(독일 연방재료연구소) 공개 방사선 사진이 원천으로 보인다.

**같은 모원본에서 나온 인접 타일이 학습과 평가로 갈리면 성능이 부풀려진다.**
이는 불변조건 1-5(중복 묶음 단위 분할)가 겨냥한 바로 그 누수이며, RIAWELC에서는
pHash를 돌릴 필요도 없이 **파일명 접두사가 곧 묶음 ID**다.

**→ 트랙 A 조치 권고:** RIAWELC ingest 어댑터는 `_[행][열]` 정규식을 떼어낸
접두사를 `group_id`로 매니페스트에 기록하고, 분할을 이 묶음 단위로 수행해야 한다.
저자 제공 분할(4-4)이 이 제약을 지켰는지는 **검증되지 않았다.** 이것도 저자 분할을
쓰지 말아야 할 이유다.

### 사용 전 확인이 필요한 사항 2건

**(a) 저해상 77장은 어노테이션이 비어 있다.** `.yolo` 파일은 존재하나 내용이 없다.

**(b) 🔴 이미지 크기가 장마다 다르다.** RIAWELC처럼 고정 규격이 아니다. 전량 3,022장 실측:

|---|---|---|---|---|
| low_resolution | 2,000 | 85 ~ 215 (155.2) | 30 ~ 56 (40.0) | 24bpp RGB |

**크기를 고정값으로 가정한 코드가 깨진다**(헤더에서 읽어야 한다). 그리고
**640 정사각 letterbox를 그대로 적용하면 세로 패딩이 과도하다** — 저해상은 세로가

**(c) 저자 제공 5-fold 분할이 들어 있다.** `kfold_low\`·`kfold_high\`가 fold별로 이미지를

> **두 데이터셋 모두 저자 제공 분할이 오염돼 있다.** 창원은 연속 촬영 묶음을 53.1% 쪼갰고,
> RIAWELC은 test를 train에서 복제했다. 저자 분할을 쓰지 않는다는 원칙(불변조건 1-3)이
> 두 번 다 옳았다.

# 7. 재현 방법 (팀원이 같은 벽을 만날 때)

## 7-1. 7-Zip

지시문은 미설치를 전제했으나 **이미 설치돼 있었다**: `C:\Program Files\7-Zip\7z.exe`.
없으면 `winget install 7zip.7zip`.

RAR 분할은 **`part01.rar`만 지정하면 19개가 자동 병합된다.** 나머지를 따로 풀지 않는다.

```powershell
& "C:\Program Files\7-Zip\7z.exe" x "RIAWELC_dataset.part01.rar" -o"<대상>" -y
```

## 7-2. 🔴 함정 — PowerShell 5.1은 `.ps1`을 ANSI로 읽는다

`G:\내 드라이브`·`G:\공유 드라이브` 처럼 **한글이 든 경로를 스크립트 파일에 그대로 쓰면 깨진다.**
UTF-8(BOM 없음)로 저장된 `.ps1`을 5.1이 ANSI로 해석해 `Illegal characters in path`로 죽는다.

**처방 — 경로를 코드포인트로 조립해 스크립트를 순수 ASCII로 유지한다.**

```powershell
# "내 드라이브"
$mydrive = -join @(0xB0B4,0x20,0xB4DC,0xB77C,0xC774,0xBE0C | ForEach-Object { [char]$_ })
# "공유 드라이브"  <- 현행 적재 위치
$shared  = -join @(0xACF5,0xC720,0x20,0xB4DC,0xB77C,0xC774,0xBE0C | ForEach-Object { [char]$_ })
$root = Join-Path "G:\" $shared
```

`curl.exe` 같은 **네이티브 exe에 한글 경로를 인자로 넘기지 마라.** `Set-Location -LiteralPath`로
먼저 이동한 뒤 상대 파일명만 넘기면 인코딩 문제가 사라진다.

## 7-3. 🔴 함정 — `Invoke-WebRequest` / `WebClient`가 조용히 잘린다

GitHub raw에서 26MB 파트를 받는데 **매번 25.7MB 근처에서 잘렸고, 예외가 나지 않았다.**
크기를 검증하지 않았다면 손상된 아카이브를 정상으로 오인했을 것이다.

**처방 — `curl.exe` + 이어받기 + 크기 검증.**

```powershell
& curl.exe -sS -L -C - --retry 5 --retry-all-errors --retry-delay 2 `
    --connect-timeout 30 --max-time 600 -o $name $url
# 받은 뒤 반드시 기대 바이트 수와 대조할 것
```

**교훈: 다운로드는 성공/실패가 아니라 바이트 수로 판정한다.**

## 7-4. Google Drive 대용량 파일 (LoHi-WELD)

100MB 초과 파일은 바이러스 검사 인터스티셜 HTML이 먼저 온다. 파일이 아니라
경고 페이지를 받아 저장하기 쉽다.

```powershell
# 1) 경고 페이지에서 세션별 uuid를 뽑고
$warn = & curl.exe -sS -L "https://drive.usercontent.google.com/download?id=$id&export=download"
$uuid = [regex]::Match(($warn -join ""), 'name="uuid" value="([^"]+)"').Groups[1].Value
# 2) confirm=t + uuid 를 붙여 다시 요청한다
& curl.exe -sS -L -C - -o $out "https://drive.usercontent.google.com/download?id=$id&export=download&confirm=t&uuid=$uuid"
```

받은 뒤 **ZIP EOCD 시그니처(`PK\x05\x06`)로 무결성을 확인**하면 HTML 오수신을 걸러낸다.

## 7-5. 드라이브 폴더 직접 해제는 느리다

RIAWELC 24,407개 소파일을 드라이브 동기화 폴더에 푸는 데 **분당 약 500개, 총 50분**이
걸렸다. 정상이며 실패가 아니다. 로컬에 풀고 복사하면 빠르지만 **로컬 사본 금지
원칙에 어긋나므로 그렇게 하지 않았다.** 시간을 잡고 시작하라.

## 7-6. 드라이브 동기화 확인 방법

**"로컬에 파일이 있다"와 "클라우드에 올라갔다"는 다르다.** G: 는 가상 파일시스템이라
아직 업로드되지 않은 파일도 정상으로 보인다. 확인 방법 두 가지를 남긴다.

**쓰지 말 것 — 드라이브 용량 대조.** `Get-PSDrive G`의 `Used`는 계정 전체 할당량이라
**다른 폴더의 동기화 활동이 섞인다.** 이번에도 우리가 올린 2.09GB에 대해 델타가
4.92GB로 나왔고 이후 감소하기까지 했다. 완료 판정 근거로 쓸 수 없다.

**쓸 것 — 클라우드 색인 직접 조회.** Drive API로 파일을 조회해 **바이트 수를 대조**한다.
이게 유일하게 확실하다.

**단, 색인 지연을 감안하라.** 대량 업로드 시 파일이 실제로 올라간 뒤에도 검색 색인에
반영되기까지 **수십 분이 걸린다.** 이번에 LoHi `dataset` 폴더는 로컬 생성 후 약 40분
지나서야 조회됐다. **색인에 안 보인다고 실패로 판단하지 마라.**

**폴더 children 조회(`parentId = '...'`)는 믿지 마라.** 하위 항목이 7개인 폴더가
3개만 반환되는 등 불완전한 결과를 준다. **파일명으로 직접 조회**해야 정확하다.

**완료 판정법.** 로컬에서 **가장 마지막에 생성된 파일**을 찾아 그 이름으로 클라우드를
조회한다. 그게 올라와 있으면 큐가 비었다는 뜻이다.

```powershell
# 로컬 최종 생성 파일 확인
Get-ChildItem -LiteralPath $root -Recurse -File |
  Sort-Object CreationTime -Descending | Select-Object -First 3 Name, CreationTime
# 그 파일명을 Drive API로 조회해 존재·바이트 수를 대조한다
```

**실측 소요.** 58,919개 2.09GB 업로드는 **해제가 끝난 뒤로도 1시간 이상** 더 걸렸다.
`GoogleDriveFS` 프로세스의 CPU 누적과 `%LOCALAPPDATA%\Google\DriveFS` 캐시 크기가
움직이면 정상 작동 중이다.
