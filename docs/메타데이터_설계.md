# 데이터셋 등록부와 실험 데이터 목록

이 문서는 자료의 출처·사용 조건·확보 상태를 기록하는 **데이터셋 등록부(registry)**와, 실제 학습·평가에 사용할 이미지를 정하는 **매니페스트(manifest)**의 역할을 설명한다. 자료를 추가하거나 검토하는 사람이 무엇을 직접 확인하고 무엇을 프로그램으로 생성해야 하는지 구분하기 위한 설계다.

처음 설계한 날짜는 2026-08-21이다. 당시 미확보였던 AI허브 자료는 이후 확보했고, 2026-08-31에는 실험 이미지 62,308장의 분할 목록을 동결했다. 이 문서는 과거 구현 제안을 현재 완료 상태와 구분해 정리했다. 2026-10-05에 확인한 코드 기준은 `main`의 `0f746772b156f7c6fc58b398f244d05547a4b1cc`다. 코드와 문서를 읽어 대조했으며 이번 개정에서 검증기나 실험을 실행하지 않았다.

현재 데이터의 규모·용도는 [데이터셋 현황](데이터셋_현황.md), 분할과 성능 해석은 [사전실험 보고](사전실험_보고.md)를 본다. 등록부의 형식 검사를 통과해도 실물 사실성, 사용권, 사람 검토, 평가셋 독립성까지 확인된 것은 아니다.

## 1. 등록부와 매니페스트의 차이

| 기록 | 한 항목의 단위 | 누가 무엇을 기록하는가 | 역할 |
|---|---|---|---|
| 데이터셋 등록부 | 데이터셋 1건 = JSON 1파일 | 사람이 출처·조건·구조·검증 근거를 기록 | 확보·활용 가능성 판단과 어댑터 구현의 참고 |
| `manifest.csv` | 이미지 1장 = 1행, 30컬럼 | 어댑터와 후속 처리 프로그램이 생성 | 이미지 식별·중복 묶음·학습/평가 분할 |
| `annotations.csv` | 결함 1개 = 1행, 18컬럼 | 원본 라벨에서 변환 | 결함 종류와 위치·기하 정보 |
| `data_capabilities.yaml` | 데이터 스냅샷 1개 | 자료가 지원하는 과업 범위를 기록 | 위치·두께·스케일의 보유 여부와 판정 범위 |
| 스냅샷과 `SNAPSHOT.sha256` | 동결한 산출물 묶음 | 정해진 파일의 해시로 검증 | 같은 입력·분할을 사용했는지 확인 |

등록부는 사람의 조사 기록이고 매니페스트는 파일 처리 결과다. 등록부를 고쳤다는 이유로 이미 동결한 분할이 바뀌어서는 안 된다. 학습·평가 코드는 검증된 스냅샷을 읽는다. 등록부나 자유 서술 `notes`를 별도 이미지 목록·분할 설정처럼 사용하지 않는다.

라벨의 의미는 `configs/label_map.yaml`, 매니페스트·주석의 컬럼과 읽기 규칙은 `data/manifest_io.py`가 관리한다. 등록부는 이 규칙을 복제하지 않고 원본 구조와 대응 근거를 설명한다. 원본에는 손대지 않으며 이미지별 수치·좌표·해시·분할은 사람이 옮겨 적지 않는다.

## 2. 저장 위치와 구현 상태

현재 확인한 등록부 관련 파일은 다음과 같다.

| 파일 | 역할·확인 상태 |
|---|---|
| `data/registry/_schema/dataset_registry.schema.json` | JSON Schema 2020-12, 스키마 버전 1 |
| `data/registry/datasets/riawelc.json` | 현재 존재하는 등록부 예시. `review_status=pending`, `eligible=false` |
| `scripts/validate_registry.py` | 스키마·의미 검사 프로그램 |
| `tests/test_registry_validator.py` | 등록부 검증 관련 테스트 파일. 이번 개정에서 실행하지 않음 |

초기 설계가 제안한 템플릿 3종, 자동 집계 `index.json`, `build_registry_index.py`, `verify_landing.py`, `link_raw.py`, 등록부 전용 README는 이 기준의 해당 경로에서 확인되지 않았다. 아래 작성 흐름에서 자동 집계·경로 검증을 설명할 때는 설계상의 역할이며 구현 완료로 읽지 않는다.

파일명은 `<dataset_id>.json`으로 두고 ID와 일치시킨다. 현재 스키마의 ID 패턴은 `^[a-z][a-z0-9_]*$`다. 초기 제안의 3~32자 제한과 다르다. `kind`는 `image`, `text_corpus`, `document` 가운데 하나다.

## 3. 사람이 확인해 기록할 내용

| 블록 | 기록할 내용 | 주의할 점 |
|---|---|---|
| `authoring` | 작성자·작성일·검토자·검토 상태 | 작성과 검토를 구분. 검토 완료일을 임의로 채우지 않음 |
| `provenance` | 발행처, 배포 URL, 판본, 접근 상태, 라이선스, 인용·재배포·반출 조건 | 공개 다운로드와 사용권을 동일시하지 않음 |
| `constraints` | 클라우드 업로드·외부 상용 API·상업 이용 조건 | 설명문과 실제 허용값이 일치해야 함 |
| `acquisition` | 취득일, 논리 저장 위치, 저장 방식, 아카이브·검증 근거 | 실제 절대경로는 공개 등록부 밖에 보관 |
| `pipeline` | 투입 여부, 원본 하위경로, 어댑터, 제외 이유 | 자료 보유가 곧 투입 가능을 뜻하지 않음 |
| `layout` | 이미지·라벨 배치, 클래스 폴더 깊이, 짝짓기 규칙 | 저자 분할 폴더를 클래스 이름으로 읽지 않음 |
| `label_vocabulary` | 원본 라벨 문자열과 통일할 결함 이름의 제안 | 원문 표기를 보존. 제안이 실제 매핑을 자동 변경하지 않음 |
| `fields_declared` | 메타데이터 항목별 존재 여부·위치·근거 | 확인하지 않은 필드 이름을 추측하지 않음 |
| `counts_announced` | 공지·확보 기록의 개수와 근거 | 파일 수·고유 이미지 수·실험 사용 수를 구분 |
| `samples` | 이미지·클래스·조치 텍스트의 제공 여부 | 예시 최대 5건. 전수 이미지 목록으로 확대하지 않음 |
| `probe_result` | 프로그램으로 확인한 결과 | 선언을 덮어쓰지 않고 별도 기록 |
| `open_items`, `notes` | 남은 확인, 방법·담당·기한, 설명 | 프로그램의 숨은 설정으로 사용하지 않음 |

현재 스키마에서 필수인 공통 키는 `registry_schema_version`, `dataset_id`, `kind`, `authoring`, `provenance`, `constraints`, `acquisition`, `pipeline`, `counts_announced`, `samples`다. 이미지 자료에는 `layout`, `label_vocabulary`, `fields_declared`를 추가로 요구한다. `$schema`를 적으면 편집기가 스키마를 참조할 수 있지만 현재 스키마의 필수 키는 아니다. `text`·`document` 블록은 존재하되 이미지처럼 세부 필드를 엄격하게 정의한 상태는 아니다.

## 4. 없다는 사실과 모른다는 상태

`fields_declared`는 다음 10항목을 사용한다. 이 목록을 고정해야 항목 누락과 구조적 부재를 구별할 수 있다.

| 항목 | 뜻 |
|---|---|
| `modality` | 검사 방식 |
| `material` | 원본이 제공한 재질·출처 구분 |
| `label_type` | `polygon`, `bbox`, `classification` 등 라벨 형태 |
| `defect_label` | 결함 이름을 읽을 원본 위치 |
| `normal_label` | 정상 표시를 읽을 원본 위치 |
| `coords` | 좌표 위치와 좌표계 |
| `thickness_mm` | 두께 필드의 위치 |
| `px_per_mm` | 픽셀-실치수 환산 필드의 위치 |
| `quality_level` | 품질 등급 필드의 위치 |
| `group_key` | 동일 원판·수집 묶음을 추적할 근거 |

각 항목의 `status`는 여섯 값으로 구분한다.

| 상태 | 의미 | 함께 기록할 내용 |
|---|---|---|
| `present` | 원본에 값이 있음 | `source_key`, `evidence` |
| `constant` | 데이터셋 전체에 적용할 상수로 선언 | `constant_value`, `evidence` |
| `absent` | 확인했으나 없음 | `evidence`, `evidence_level` |
| `out_of_contract` | 원본에 있지만 현재 데이터 규약의 값 공간 밖 | `observed_value`, `evidence` |
| `not_applicable` | 해당 자료에 적용할 개념이 아님 | 적용되지 않는 이유를 설명 |
| `unverified` | 아직 확인하지 못함 | `how_to_verify`, `owner`, `due` |

현재 스키마의 `evidence_level` 값은 `full_scan`, `file_inspected`, `publisher_doc`, `inference`, `none`이다. 각각 전수 확인, 파일 확인, 배포처 문서, 추론, 근거 없음의 구분이다. 초기 문서에 있던 `sample_inspected`는 현재 허용값이 아니다. 표본을 읽었다면 `file_inspected`와 함께 표본 범위를 설명한다.

`null`만 적으면 미확인·부재·해당 없음이 구별되지 않는다. 상태 객체로 그 의미를 표시하되 `null`을 모든 위치에서 금지하지는 않는다. 현재 스키마는 `probe_result`, 정상 라벨의 `proposed_l2` 등에서 제한적으로 허용한다. `coverage`는 사람이 입력하는 선언에서 `null`만 허용하며 실측 보유율은 별도로 기록한다.

RIAWELC의 `material=UNK`는 원본이 재질 정보를 주지 않는다는 값이다. `px_per_mm=absent`는 환산 정보가 없음을 뜻한다. `group_key`는 메타데이터 필드가 없어도 파일명 접두사에서 얻을 수 있으므로 `present`와 `source=filename_pattern`으로 기록한다. 현재 `source` 허용값은 `metadata_field`, `filename_pattern`, `dirname`, `absent`다.

창원 ST·AL도 제공 라벨의 존재와 실제 재질의 정확성을 구분해야 한다. 필드 보유율 100%는 의미 정확도 100%가 아니다. 현행 재질 해석은 [데이터셋 현황](데이터셋_현황.md)을 따른다.

## 5. 실험 파일의 값은 어디서 생기는가

### 이미지 목록 30컬럼

| 컬럼 | 생성 근거 |
|---|---|
| `image_id`, `source`, `rel_path` | 어댑터의 자료 ID와 원본 상대경로. `image_id`는 `source:rel_path` |
| `sha256`, `width_px`, `height_px` | 파일 바이트와 이미지 헤더 |
| `modality`, `material`, `label_type` | 원본 정보 또는 근거를 명시한 어댑터 상수 |
| `has_defect`, `n_defects`, `defect_types`, `iso_codes`, `src_labels_raw` | 원본 라벨과 `label_map.yaml` |
| `has_localization` | 라벨이 위치 정보를 제공하는지 여부. `label_type`과의 정합성 확인 필요 |
| `phash_hex`, `group_id`, `group_size` | 중복·유사 이미지 처리 결과 |
| `strata_key`, `split`, `client`, `eval_subset` | 묶음별 층화와 분할 결과 |
| `thickness_mm`, `thickness_source`, `px_per_mm`, `scale_source`, `quality_level` | 실제 메타데이터와 근거 구분. 없는 값은 임의의 수치로 채우지 않음 |
| `ingest_version`, `label_map_version`, `notes` | 처리·매핑 버전과 설명 |

`defect_types`와 `iso_codes`는 각각 정렬된 목록이므로 i번째 값끼리 대응한다고 가정하지 않는다. 개별 결함의 코드 연결은 주석 행과 사상표에서 읽는다.

### 결함 주석 18컬럼

| 컬럼 | 생성 근거 |
|---|---|
| `ann_id`, `image_id` | 이미지 식별자와 결함 순번 |
| `src_label_raw`, `defect_type`, `iso_code` | 원본 라벨과 사상표 |
| `polygon_json` | 원본 좌표 보존 |
| `bbox_x1_px`, `bbox_y1_px`, `bbox_x2_px`, `bbox_y2_px` | 폴리곤 최소·최대, floor/ceil, 이미지 경계 제한 |
| `area_px`, `major_axis_px`, `minor_axis_px`, `equiv_diameter_px` | 폴리곤·기하 계산 |
| `major_axis_mm`, `equiv_diameter_mm` | 검증된 `px_per_mm`가 있을 때만 환산 |
| `geom_valid`, `geom_flags` | 좌표·기하 이상 표시 |

행 수준 결측도 구분한다. 위치 라벨이 없는 분류 자료(RIAWELC)는 결함 종류는 알지만 기하값이 없다. 정상 이미지는 결함 객체가 없다. 스케일이 없는 이미지는 픽셀 위치가 있어도 mm 값을 만들 수 없다. 이 세 경우를 모두 0으로 채우면 서로 다른 데이터 상태가 같은 값으로 바뀐다.

등록부에는 이미지별 해시·좌표·면적·분할 등을 직접 넣지 않는다. 원본 아카이브 해시는 출처 검증 정보이므로 예외적으로 `acquisition.archives`에 기록한다. 정상은 결함 종류 목록의 별도 유형이 아니며 정상 라벨의 `proposed_l2`는 `null`이다.

## 6. 판정 범위는 메타데이터 확인과 별도로 결정한다

`verdict_mode`는 `absolute`(실측 치수), `conditional`(명시한 가정 조건), `clause_only`(조항 검색 범위)를 구분한다. 등록부에는 가정 두께·환산값·판정 결과를 넣지 않는다. 현재 창원 자료에는 두께·스케일이 없어 이미지 과업을 실치수 합부 판정으로 승격할 근거가 없다.

초기 설계는 관련 보유율 0.95 이상을 실측 치수 모드 후보 조건으로 검토했다. 현재 `data/ingest/base.py`에는 두께와 스케일 보유 조건으로 `ABSOLUTE`를 자동 선택하는 코드가 남아 있다. 이 동작은 사람의 적용 범위 검토를 대신하지 않으며, 다른 데이터셋을 추가할 때 자동 승격 경로를 점검해야 한다. Intel에 `THICKNESS_MM`가 기재돼 있다는 사실도 창원 이미지의 누락 정보를 채우거나 현행 과업 범위를 바꾸지 않는다.

원본에 없는 두께·치수·판정·조치를 합성할 경우 그 근거와 가정을 별도 기록한다. 규정 문서의 추출 성공, 생성 모델의 응답, 자동 검증 통과를 사람 정답 검증 완료로 표시하지 않는다.

## 7. 경로·보관·사용 조건

경로는 논리 위치, 실제 위치, 검증 결과를 나눈다. 등록부에는 `gdrive:weld-fl-datasets/RIAWELC` 같은 논리 URI와 `raw_subdir`, `dataset_subpath`를 적는다. 실제 드라이브 절대경로는 `configs/paths.local.yaml` 같은 비추적 설정에 둔다. `configs/*.local.yaml` 무시 규칙을 추가한 기록은 2026-09-15에 확인됐다.

매니페스트의 `rel_path`는 저장소 기준 POSIX 상대경로다. 수집 폴더명이나 로컬 드라이브 경로가 식별자에 섞이면 `image_id`가 바뀌어 기존 분할과 연결되지 않을 수 있다. 정션·심볼릭 링크의 실제 동작과 경로 왕복은 사용하는 장비에서 확인해야 하며, 초기 연결 제안을 검증 완료로 읽지 않는다.

원본 아카이브·해제본은 읽기 전용으로 취급하고 변환 결과를 그 아래에 쓰지 않는다. RIAWELC의 대괄호 파일명을 glob 패턴으로 직접 조회하면 문자 클래스로 해석될 수 있으므로 실제 경로 읽기와 파일 탐색 패턴을 구분한다.

사용 조건은 저장 위치보다 먼저 확인한다. 프로젝트의 AI허브 자료 취급 규약은 국내 장비 이용과 외부 전송 제한을 전제로 한다. 과거 공유 드라이브 적재 기록이 있다는 이유로 이 조건이 해소됐다고 보지 않는다. RIAWELC·LoHi-WELD도 LICENSE 파일 부재 상태에서 모든 이용·재배포가 자유롭다고 단정하지 않는다. 외부 API·클라우드·상업 이용 허용값은 확인 근거에 맞게 관리해야 한다.

## 8. 현재 검증기가 검사하는 것과 검사하지 않는 것

아래 명령은 등록부 디렉터리를 검사하는 현재 인터페이스다. 단일 JSON 파일을 위치 인자로 받는 초기 예시와 다르다.

```powershell
uv run python scripts/validate_registry.py
uv run python scripts/validate_registry.py --registry-dir data/registry/datasets --strict
```

| 검사 | 현재 코드에서 확인한 범위 |
|---|---|
| 저장 형식 | UTF-8, BOM·CRLF·스마트쿼트 검사 |
| JSON·스키마 | 파싱과 JSON Schema 2020-12 검사. `jsonschema` 미설치 시 스키마 검사를 건너뛰었다고 출력 |
| 식별자·수기 계산값 | 파일명과 `dataset_id` 일치, 금지된 계산 필드, 절대경로 확인 |
| 상태별 근거 | `status`별 동반 필드, 선언 `coverage`의 수치 입력 금지 |
| 라벨 | `proposed_l2`와 사상표 대조, `eligible=true`일 때 원본 라벨 매핑 확인 |
| 사용 조건 | 클라우드 URI와 `cloud_upload=false`의 충돌, 인용 요구와 인용 목록 확인 |
| 투입 상태 | 투입 가능 자료의 원본 하위경로·어댑터·`ready`·`in_hand` 확인 |
| 검토·미결 | 검토 완료 상태의 작성자/검토자 동일 여부, 미결 항목의 기한 |

오류가 있으면 종료코드 1, 없으면 0이다. `--strict`에서는 경고도 실패로 처리한다. 초기 문서의 0/1/2/3 종료코드와 B/D 자동 분류는 구현된 기능이 아니다. B는 착수를 막는 미확인 항목, D는 후속 확인에 맡기는 항목이라는 설계상의 우선순위로만 남아 있다.

이 검증기는 실물 파일과 선언의 전수 일치, 약관의 법적 해석, 실제 업로드 이력, 전문가 검토, 모든 실행 경로의 규약 준수까지 검사하지 않는다. 초기 제안의 유료 문서 색인 금지 조건이나 `unverified` 등급별 차단이 모두 구현됐다고도 볼 수 없다. 스키마 검사 생략 메시지와 경고를 포함해 결과를 읽어야 한다.

## 9. RIAWELC 예시를 읽는 법

현재 예시는 완성된 운영 설정이 아니다. 작성일 2026-08-21, 검토 상태 `pending`, `pipeline.eligible=false`, `adapter_state=blocked`이며 상업 이용·재배포·저장 연결의 미확인 사항이 남아 있다.

파일에는 매핑이 실물과 다르다는 과거 제외 이유가 남아 있지만, 현재 `label_map.yaml`에는 `Difetto1`, `Difetto2`, `Difetto4`, `NoDifetto` 매핑이 반영돼 있다. `RiawelcAdapter`도 재귀 탐색으로 이미지의 부모 폴더를 클래스로 읽고, ` - Copia` 접미를 포함한 파일명에서 원판 접두사를 얻는다. **코드 일부가 수정됐다는 사실만으로 등록부의 검토 상태나 활용 승인을 자동 갱신하지 않는다.**

예시의 `images_total=24407`은 원본 파일 수다. 고유 이미지는 21,964장이며 `testing` 2,443개가 `training`의 동일 사본이라는 사실을 함께 읽어야 한다. 이미지 규격은 227×227, 위치 라벨은 없고, 원판 접두사는 후속 확인값 479개다. 이전 509개 집계의 경위는 [실물 확보 보고](데이터셋_실물확보.md)에 정리했다.

## 10. 다음 등록·검토에 필요한 순서

1. 배포처·판본·접근 상태와 사용 조건을 확인하고 자료 ID를 정한다.
2. 실제 파일 배치와 라벨을 확인해 선언과 근거를 적는다. 미확인 항목에는 확인 방법을 남긴다.
3. 이미지별 값은 어댑터로 만들고 선언과 실측을 따로 보존해 대조한다.
4. 등록부 검사와 별도의 사람 검토를 거쳐 사용 범위를 정한다.
5. 원본·매핑·분할·파생물의 버전을 기록하고 동결 결과를 검증한다.

초기 제안 중 등록부 자동 집계, 저장 경로 검증, 값 공간·상대경로의 추가 불변식, 판정 모드 승격의 명시 통제, 스냅샷에 출처 정보를 연결하는 방식은 별도 구현·확인 사항이다. 과거 마감일이나 검증기 오류 0건이라는 기록만으로 완료 처리하지 않는다. 공개 QA 자료는 현재 조사 기록이며 실제 코퍼스 투입에서 제외한 방침을 유지한다. 출처·권리와 학습 적합성을 확인한 뒤에야 그 상태를 바꿀 수 있다.
