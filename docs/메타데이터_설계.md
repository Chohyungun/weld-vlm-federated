# 0. 이 문서가 정하는 것: 한 장 요약

8/16 회의가 "창원(AI허브 71761) 메타데이터를 기준 스키마로 한 **JSON 인덱스**를 만든다"로
정했다. 그 뒤 검토에서 계약 #1(`configs/label_map.yaml`)과
계약 #2(`manifest.csv` + `annotations.csv` + 로더)가 **동결**됐다.

지금 아무나 JSON 스키마를 새로 그리면 파이프라인에 안 들어가는 **두 번째 스키마**가 생긴다.
그래서 이 문서는 JSON 인덱스의 **정체**부터 못 박는다.

> **JSON 인덱스는 매니페스트가 아니다. 매니페스트를 만들 어댑터에게 보내는 발주서다.**
> 그레인(한 항목의 단위)이 이미지가 아니라 **데이터셋**이다.
> 이름을 **등록부(registry)** 로 부른다.

```
[사람]  data/registry/datasets/<id>.json        ← 손으로 쓰는 유일한 곳
          │
          ├─ scripts/validate_registry.py       (스키마 + 계약 대조 + 레드라인 검사)
          ├─ scripts/build_registry_index.py → index.json   (8/23 회의 제출물, 기계 생성)
          │
          └─ [검토 → 승인] ─────→ configs/label_map.yaml  sources.<id>   (계약 #1)
                                 └─→ data/ingest/<id>.py     어댑터 상수      (계약 #2)
                                           │
                                           └─→ manifest.csv / annotations.csv  (전부 기계 생성)
```

**흐름은 한 방향뿐이다.** 학습·평가·채점 코드는 등록부를 **읽지 않는다.**
예외는 `scripts/link_raw.py`(수집 폴더를 `data/raw/`에 잇는 운영 배선) 하나뿐이고,
그건 실험 데이터가 아니라 배선이다.

이 한 방향 규약이 "두 번째 스키마"를 원천에서 막는다. 등록부가 틀려도 매니페스트가
안 바뀌고, 등록부를 고쳐도 잠긴 스냅샷이 안 바뀐다.

# 1. 왜 이미지 단위 인덱스를 만들면 안 되는가

이건 취향이 아니라 산수와 계약의 문제다. 세 가지 이유가 각각 독립적으로 치명적이다.

## 1-1. 계약 #2와 그레인이 정면 충돌한다

계약 #2가 이미 **이미지 1장 = 1행**(manifest, 30컬럼)과 **결함 1개 = 1행**(annotations, 18컬럼)을
점유하고 있다. 같은 그레인의 JSON을 또 만들면 같은 사실에 진실이 둘이 되고,
불변조건 1-2("매니페스트가 단일 진실")가 그 자리에서 깨진다.

## 1-2. 사람이 알 수 있는 값이 없다

manifest 30컬럼 중 `sha256` · `phash_hex` · `group_id` · `group_size` · `strata_key` ·
`split` · `client` · `eval_subset` · `width_px` · `height_px` 는 **정의상 계산 결과**다.
annotations 18컬럼은 전부 폴리곤에서 파생된 기하값이다. 사람이 옮겨 적으면
불변식 IV1~IV12가 통째로 깨진다.

## 1-3. 시간이 안 된다

```
7만 장 × 1장당 10초 (경로 확인 + 라벨 확인 + 타이핑, 낙관적 하한)
  = 700,000초 = 194.4 시간 ÷ 3인 = 64.8 시간/인 ÷ 6일 = 하루 10.8 시간/인
```

파일 크기로도 안 된다. 최소 필드만 넣어도 약 8 MB, 전체 필드면 약 28 MB다.
`git diff`가 의미를 잃고, 손으로 열 수 없는 파일이 된다.

**등록부 규모는 이렇다.**

| | 이미지 단위 | **데이터셋 단위 (채택)** |
|---|---|---|
| 항목 수 | 62,998 (AI허브 RT만) | 15~20 (전 데이터셋·말뭉치·문서) |
| 1건 작성 | 10초 | 40~90분 |
| `index.json` 크기 | 8~28 MB | 약 80 KB |
| 오타 1건의 영향 | 이미지 1장 (발견 불가) | 데이터셋 전체 (**검증기가 잡는다**) |

> **한 줄로:** 데이터셋 수준 메타데이터는 사람이, 이미지 수준 메타데이터는 어댑터가 만든다.

# 2. 파일 배치와 최상위 키

## 2-1. 데이터셋 1건 = 1파일

```
data/registry/
├── _schema/dataset_registry.schema.json   # 스키마 정본. A 소유, 다른 사람 편집 금지
├── _TEMPLATE_image.json                   # 복사해서 시작. 전 필드가 "unverified" 선기입
├── _TEMPLATE_text_corpus.json
├── _TEMPLATE_document.json
├── datasets/                              # ← 사람이 손으로 쓰는 유일한 디렉터리
│   ├── riawelc.json              (예서)
│   ├── lohi_weld.json            (예서)
│   ├── aihub71761.json           (예서)
│   ├── notre_dame_95.json        (예서)
│   ├── ...
│   ├── hf_<name>.json            (상은)
│   └── std_<doc_id>.json         (조현건)
├── index.json                             # 기계 생성. 손 편집 금지
└── README.md                              # 팀원용 1페이지 지시
```

1파일로 쪼개는 이유는 **git 충돌 원천 제거**다. 하나의 큰 JSON 배열이면 3인이 같은 배열의
비슷한 줄을 동시에 건드려 병합 충돌이 사실상 확정되고, JSON 충돌 해소는 CSV보다 위험하다
(괄호 짝이 깨진 채 커밋된다). 파일이 다르면 텍스트 병합 충돌이 원리적으로 발생하지 않는다.

회의 제출물이 "하나의 JSON 인덱스"여야 한다는 요구는 `index.json`이 충족한다.
그건 **집계 산출물**이고, 손으로 쓰는 단위는 여전히 데이터셋 1건이다.

파일명 = `dataset_id` + `.json`. `dataset_id`는 `^[a-z][a-z0-9_]{2,31}$`.
**파일명에 담당자 이름을 넣지 않는다**. 담당이 바뀌면 파일명이 바뀌고, 파일명이 바뀌면
git이 삭제+추가로 보아 이력이 끊긴다. 담당자는 `authoring.owner` 필드로만 표시한다.

## 2-2. 최상위 키 16개

| # | 키 | 필수 | 내용 |
|---|---|---|---|
| 1 | `$schema` | ✔ | `"../_schema/dataset_registry.schema.json"`. **이 한 줄이 VS Code에서 자동완성·실시간 오타 검사를 켠다.** 설치 비용 0, 예방 효과 최대 |
| 2 | `registry_schema_version` | ✔ | 정수. 현재 `1` |
| 3 | `dataset_id` | ✔ | 파일명과 일치. `kind=image`이고 `pipeline.eligible=true`면 계약 #1 `sources` 키·어댑터 `source` 상수와 **3중 일치** |
| 4 | `kind` | ✔ | `image` \| `text_corpus` \| `document`. 이 값이 이하 필수 키 집합을 가른다 |
| 5 | `authoring` | ✔ | `owner` · `written_at` · `reviewer` · `reviewed_at` · `review_status`. 8/16 "LLM 결과는 사람이 1회 검증" 조항의 기계 표현 |
| 6 | `provenance` | ✔ | **원천·출처.** 발행처 · URL · 판본 · 접근조건 · 라이선스 · 인용의무 · **반출 제약** |
| 7 | `acquisition` | ✔ | **경로(수집 쪽).** 어디에 받았는가, 어떤 상태인가 |
| 8 | `pipeline` | ✔ | **경로(파이프라인 쪽) + 투입 여부.** `eligible` · `raw_subdir` · `dataset_subpath` · `adapter` |
| 9 | `constraints` | ✔ | 6의 값화. 클라우드 업로드·외부 API·상업 이용 가부. **검증기가 읽는 레드라인 필드** |
| 10 | `layout` | image | 파일 배치 규칙. 어댑터 `discover()`의 입력 명세 |
| 11 | `label_vocabulary` | image | 원본 라벨 어휘 전량 + L2 사상 제안 |
| 12 | `fields_declared` | image | **기준 스키마 10키 보유 선언표.** 이 설계의 심장 (§3·§5) |
| 13 | `counts_announced` | ✔ | 공지·실측 수량 + `basis` + `verified: false` |
| 14 | `samples` | ✔ | 8/16 샘플구조 ①②③ + 실물 예시 ≤5건 |
| 15 | `probe_result` | . | 기계 실측 결과. **사람이 쓰지 않는다.** 없으면 `null` |
| 16 | `open_items` · `notes` | . | 미해결 사항 (등급·확인방법·담당·기한 필수) / 자유 서술 |

`kind=text_corpus`와 `kind=document`는 10~12를 요구하지 않고 대신 `text`/`document` 블록을 갖는다.
JSON Schema의 `if/then`으로 갈라, 이미지 담당자에게 조항 필드를 요구하지 않고
문서 담당자에게 bbox 필드를 요구하지 않는다.

모든 객체에 `additionalProperties: false`를 건다. 키 오타가 조용히 통과하는 경로를 없앤다.

## 2-3. 이미지 배열은 **넣지 않는다**

`samples.examples`가 유일한 배열이고 스키마에서 **`maxItems: 5`로 물리적으로 막는다.**

캡이 없으면 "샘플 100개만 더 있으면 검증이 편하다"가 반드시 나오고, 그 순간 두 번째
이미지 인덱스가 완성된다. 그리고 한 번 생기면 하류가 그걸 읽기 시작한다.

# 3. 필드 대응표: 이 문서의 핵심

구분 표기:

- **[사람]**. 사람이 손으로 적는다. 안 적으면 어댑터가 값을 만들 수 없다
- **[어댑터]**. `data/ingest/*`가 파일 바이트·원본 라벨에서 만든다. **사람이 적으면 안 된다**

# 5. 결측 표기 규약: "없다"와 "모른다"를 갈라놓는 법

이 절이 등록부의 실효성을 결정한다. 이게 흔들리면 나머지가 전부 종이 위 규약이 된다.

## 5-1. 층위를 먼저 구분한다

| 층위 | 결측의 뜻 | 판별 |
|---|---|---|
| **등록부** (수집 시점) | 이 데이터셋이 이 필드를 주는가 / 우리가 확인했는가 | 아래 `status` 6값 |
| **매니페스트** (파이프라인) | 이 행에 값이 있는가 | 계약 #2 §2-3 N1/N2/N3 |

계약 #2의 N1(구조적 부재) / N2(정상 이미지) / N3(파생 불가)는 **행 수준**이고,
등록부는 그 앞단인 **데이터셋 수준**이다. 둘을 혼동하면 안 된다.

**N2는 등록부에 나타나지 않는다.** "정상 이미지"는 이미지 1장의 속성이지 데이터셋의 속성이
아니다. 등록부가 하는 일은 `label_vocabulary.labels[]`에 `is_normal: true`인 항목이
있는지 표시하는 것뿐이다.

## 5-2. JSON literal `null`을 의미 전달자로 쓰지 않는다

손으로 쓴 `null`은 "없음을 확인했다"와 "적는 것을 빠뜨렸다"가 **구별되지 않는다.**
빈 문서에서 시작하는 사람은 후자를 대량 생산한다. 그리고 JSON 파서·YAML 왕복·pandas 로딩에서
조용히 의미가 바뀐다. 계약 #2가 `keep_default_na=False`를 강제한 것과 같은 이유다.

대신 **필드를 객체로 만들고 `status` enum을 갖게 한다.**

## 5-3. `status` 6값

| 값 | 뜻 | 필수 동반 필드 |
|---|---|---|
| `present` | 원본이 값을 준다 | `source_key` (모르면 `"unverified"` 허용. 아래 주3) · `evidence` |
| `constant` | 원본은 침묵하지만 **사람이 상수로 단언**한다 | `constant_value` · `evidence` |
| `absent` | **확인했고 없다** | `evidence` · `evidence_level ∈ {file_inspected, publisher_doc}` |
| `out_of_contract` | **값은 있는데 계약 #2 값 공간에 담을 수 없다** | `observed_value` · `evidence` |
| `not_applicable` | 이 `kind`에 애초에 의미 없는 항목 | . |
| `unverified` | **아직 확인하지 않았다** (템플릿 기본값) | `how_to_verify` · `owner` · `due` |

> **주3 "있는 건 아는데 키 이름은 모른다"를 표현할 수 있어야 한다.**
> AI허브 데이터셋 페이지에 재질 ST/AL 구분이 있다는 것은 확인됐지만, 그게 JSON 필드인지
> 폴더 경로인지는 실물을 못 봐서 모른다. 이때 `status: "present"` + `source_key: "unverified"`가
> 정답이다. `source_key`에 그럴듯한 점표기 경로를 지어내면 그게 곧 추측이고, probe가
> 그 키를 못 찾아 ingest가 죽거나 잘못된 키에서 쓰레기를 읽는다.

### `out_of_contract`가 왜 필요한가

LoHi-WELD·Intel·MWDD의 `modality`는 **가시광**이다. `absent`(없다)도 `not_applicable`(무의미)도
`unverified`(미확인)도 아니다. **있는데 `RT|VT`에 안 들어간다.** 이걸 `unverified`로 적으면
거짓 진술이 되고(가시광이라는 것은 이미 확인된 사실이다), 나중에 "조사가 안 끝났다"로 오해된다.
`out_of_contract`는 그 자리에서 계약 확장 검토 목록에 자동 적재된다.

### `absent`와 `constant`를 헷갈리지 않는 법 (RIAWELC 실례)

- `material`: 재질은 RT 이미지에 **적용되는 축**이고 원본이 안 준다 →
  `constant` + `constant_value: "UNK"`. `UNK`는 결측이 아니라 값이다. 층화 키에
  `UNK|crack`으로 들어가고 재질 축이 상수가 되어 자동 소거된다.
- `px_per_mm`: 스케일은 적용되는 축인데 **없다** → `absent`. `_mm` 컬럼 전부 null,
  IV5가 검사, `verdict_mode: clause_only`.
- `group_key`: 메타데이터 필드는 없지만 **파일명에 있다** → `present` +
  `source: "filename_pattern"`. 아래가 이 축이 필요한 이유다.

### `group_key.source` 3값: 없으면 실제로 누수가 난다

```json
"group_key": {
  "status": "present",
  "source": "filename_pattern",
  "source_key": "^(?P<prefix>.+?)_\\[\\d+\\]\\[\\d+\\](?P<suffix>.*)\\.png$",
  "evidence": "...",
  "evidence_level": "full_scan"
}
```

`source ∈ {metadata_field, filename_pattern, absent}`.

RIAWELC 파일 24,407장(고유 21,964장)은 독립 표본이 아니라 **방사선 원판을 격자로 잘라낸 타일**이다
(`RRT-101R_Img1_A80_S1_[12][8].png` → `_[행][열]`을 떼면 모원본 **479개**). 메타데이터 필드는
없으니 `source` 축이 없으면 정직한 기입이 `absent`이고, 그 값이 A를 **틀린 결론**으로 끌고 간다 
묶음 ID가 파일명에 공짜로 들어 있는데 등록부는 "없음"으로 보고한다.
스펙 §6-10이 "같은 원판에서 잘린 비겹침 패치는 pHash가 원리적으로 못 잡는다"고 경고한
바로 그 지점이고, 이건 불변조건 1-5가 겨냥한 누수다.

> **⚠ 정규식을 느슨하게 써야 한다. 이 문서를 쓰면서 실측으로 발견했다.**
> 파일 30건이 `RRT-40R_Img3_A80_S2_[1][77] - Copia.png` 처럼 **`_[행][열]` 뒤에 ` - Copia`가
> 붙어 있다**(이탈리아어 "복사본"). 끝을 `.png$`로 못 박은 엄격한 정규식으로 잡으면 이 30건이
> 패턴 불일치로 떨어져 **각각 독립 묶음이 되고, 그게 곧 누수다.** 위 예시의 느슨한
> 정규식(`.+?` + `(?P<suffix>.*)`)이 24,407/24,407 전건을 잡는다.
>
> **`docs/데이터셋_실물확보.md` 4-5의 "모원본 509개"는 정정이 필요하다. 실제는 479개다.**
> 479 + (` - Copia` 30건을 각각 독립으로 센 것) = 509로 계산이 맞아떨어진다. 실측 재현:
>
> ```
> 엄격 정규식  ->  prefix 478 + 패턴 불일치 30
> 느슨 정규식  ->  prefix 479 + 패턴 불일치  0     <- 이쪽이 맞다
> ```
>
> 표본 8건을 확인한 결과 ` - Copia` 파일은 데이터셋 안에 짝이 되는 원본이 없다(중복 파일이
> 아니라 이름만 그렇게 남은 것). 같은 모원본에 속하므로 느슨한 정규식이 올바르게 묶는다.
>
> **이것이 `evidence_level`을 4단으로 나눈 이유의 실례다.** 이 오류는 `full_scan`이 아니면
> 발견되지 않고, 상류 문서를 그대로 믿었으면 30건이 조용히 평가셋으로 샜다.

## 5-4. `evidence` + `evidence_level`: 이 규약의 실효성이 여기 걸린다

```
evidence_level : "none" | "publisher_doc" | "sample_inspected" | "full_scan"
```

| 값 | 뜻 |
|---|---|
| `none` | 아무것도 안 봤다 (`unverified` 전용) |
| `publisher_doc` | **데이터셋 페이지·README·논문에 그렇게 적혀 있다.** 확정이 아니다 |
| `sample_inspected` | 실물 표본을 열어 확인했다 |
| `full_scan` | 전수 확인했다 |

**규칙. `status ∈ {present, constant, absent, out_of_contract}`인데 `evidence`가 비어 있으면
검증기가 하드 실패시킨다.** 근거 없는 `absent`는 `unverified`를 `absent`로 위장한 것이고,
그게 이 과제가 지목한 정확한 실패 양상이다.

`evidence`에는 **무엇을 언제 봤는지**를 적는다. "페이지 확인함" 같은 무내용 문자열은
형식만 채운다. 최종적으로 A가 파일을 직접 읽어야 하고, 그 검토 시간(파일당 15분)을
일정에 넣어 뒀다.

> `publisher_doc`이 확정이 아니라는 것이 이 4단의 존재 이유다. 스펙 §4-1이
> "설명서를 믿지 않는다"고 못 박았고, F 실측이 그걸 증명했다. RIAWELC 공식 README의
> "224×224"가 틀렸다.

## 5-5. 선언과 실측을 **나란히** 둔다: 덮어쓰지 않는다

```json
"probe_result": {
  "_generated_by": "data/ingest/probe_metadata.py",
  "_generated_at": "2026-08-26T14:00:00+09:00",
  "_do_not_hand_edit": true,
  "thickness_mm": {"status": "absent",  "coverage": 0.0, "keys_scanned": 41, "candidates_matched": []},
  "material":     {"status": "present", "source_key": "images.0.meta.mat_cd", "coverage": 1.0,
                   "values_seen": ["ST", "AL"]}
}
```

**`probe_metadata.py`는 `fields_declared`를 덮어쓰지 않는다.** 나란히 두고 대조하며,
불일치 건수가 게이트 보고 항목이 된다. 덮어쓰면 "사람이 뭘 잘못 알고 있었는지"가 사라지고,
그건 다음 데이터셋에서 같은 실수를 반복하게 만드는 정보 손실이다.
위 예에서 사람은 `meta.material`로 적었고 실제는 `images.0.meta.mat_cd`였다. **그 차이가
기록으로 남는 것이 설계 의도다.**

`coverage`는 `probe_result`에만 존재한다. 사람이 쓰는 `fields_declared`에는 이 키가 없다.

## 5-6. `unverified` 2등급: 차단과 위임을 가른다

전부 차단하면 승인 전에 등록부를 쓸 수 없고(8/23 초과), 전부 통과시키면 추측이 확정으로 굳는다.

| 등급 | 필드 | 규칙 |
|---|---|---|
| **B (차단)** | `label_vocabulary.label_field` · `labels[]` · `layout.{image_glob, class_dir_depth, label_mode}` · `pipeline.{raw_subdir, dataset_subpath}` · `acquisition.storage_mode` · `provenance.{license.name, citation_required, export_restriction}` | `unverified`면 **ingest 착수 금지.** 법적 항목과 경로 항목은 모르는 상태로 진행하는 것 자체가 사고다 |
| **D (위임)** | `fields_declared`의 `thickness_mm` · `px_per_mm` · `quality_level` · `group_key` · `coords.source_key` · `license.commercial_use` · `edition.*` | ingest 착수는 허용. **스냅샷 잠금 시점에는 `unverified`가 0개여야 한다**. probe 결과로 present/absent가 확정돼 있어야 한다 |

`license.commercial_use`를 D로 둔 이유: 반출 제약과 인용 의무는 착수 조건이지만
상업 이용 가능 여부는 논문·사업화 단계에서 필요한 정보다. B로 두면 "착수하려면 뭐라도 적어야
한다"는 압력이 생기고, 그 압력이 정확히 날조를 만든다.

```
$ uv run python scripts/validate_registry.py data/registry/datasets/aihub71761.json
[B] 차단 unverified 3건. ingest 착수 불가
      label_vocabulary.label_field
      layout.image_glob
      pipeline.dataset_subpath
[D] 위임 unverified 6건. probe_metadata.py 대상 (잠금 전 해소 필수)
      fields_declared.thickness_mm / px_per_mm / quality_level / group_key / coords.source_key
      provenance.license.commercial_use
[!] out_of_contract 0건
exit 2      (하드실패=3 / B잔존=2 / D만잔존=1 / 전부해소=0)
```

exit code를 4단으로 두어 CI·게이트가 "착수 가능하나 잠금 불가" 상태를 표현할 수 있게 한다.

## 5-7. 어댑터·계약 해석표: 등록부 값이 매니페스트에서 무엇이 되는가

| `status` | `evidence_level` | probe `coverage` | manifest 23/25/27 | 24/26 (`*_source`) | `capabilities` | `verdict_mode` |
|---|---|---|---|---|---|---|
| `present` | `full_scan` | ≥ 0.95 | 값 | `metadata` | `true` | **`absolute` 후보 → 확정 승인 필요**  |
| `present` | `full_scan` | < 0.95 | 있는 행만 값 | 행별 `metadata`/`none` | **`false`** | `clause_only`. **부분 보유는 전부-아니면-전무** |
| `present` | `publisher_doc` | 미실측 | null | `none` | `false` | `clause_only` |
| `constant` | . | . | 상수 | `metadata` | 상수 축 소거 | 층화에서 자동 퇴화 |
| `absent` | `file_inspected`/`publisher_doc` | . | null | `none` | `false` | `clause_only` (N3 경로, `MetricStatus.NO_SCALE`) |
| `out_of_contract` | . | . | . | . | . | **ingest 차단.** 계약 확장 검토 |
| `not_applicable` | . | . | null | `none` | 계산 제외 | 결과표 `N/A` |
| `unverified` | . | . | . | . | . | **`clause_only` 유지.** B등급이면 착수 차단 |

**`assumed`는 어느 경로로도 등록부에서 나오지 않는다.** `thickness_source="assumed"`는
가 `conditional`을 승인한 뒤 `data_capabilities.yaml`의 `assumptions` 블록에서만 발생한다.

## 5-8. 알려진 정보 손실: 정직하게 적어 둔다

`absent`(확인했고 없다)와 `unverified`(아직 안 봤다)는 **매니페스트 행에서는 구별되지 않는다.**
둘 다 `thickness_source="none"`이다. 계약 #2가 동결이라 enum에 4번째 값을 넣을 수 없고,
넣어서도 안 된다. **매니페스트는 실측 산출물이고, 실측하지 않은 것은 매니페스트에 들어갈
자격이 없다.** enum이 `metadata|assumed|none` 3값뿐인 것은 결함이 아니라 설계다.

구별은 (a) `data_capabilities.yaml`과 (b) 해당 데이터셋의 등록부 파일에 남는다.
스냅샷 하나 = 소스 하나이므로 행 수준에서 잃는 정보는 없다. 다만 D·E가 논문에 출처·라이선스·
미확인 상태를 실으려면 스냅샷 밖 파일을 봐야 하므로 §10 미해결 사항로 올린다.

## 5-9. 3종이 섞이면 실제로 무엇이 깨지는가

| 혼동 | 결과 |
|---|---|
| `unverified` → `absent`로 취급 | capability가 `false`로 **굳는다.** 실제로 두께가 있어도 `clause_only`에 갇히고, probe를 돌릴 이유가 사라진다. 결정 G가 열어 둔 승격 경로가 죽는다 |
| `absent` → `unverified`로 취급 | 끝나지 않는 확인 목록이 생기고 8/23·8/25 시한을 태운다 |
| `unverified` → `present`로 취급 (추측) | **최악.** probe가 키를 못 찾아 ingest가 죽거나, 잘못된 키에서 쓰레기 숫자를 읽어 `absolute`로 조용히 승격한다. 그 상태로 나온 "판정 정합성 95%"는 심사에서 즉시 무너진다 |
| `out_of_contract` → `present`로 취급 | 계약 enum에 없는 값이 매니페스트에 들어간다. **지금 이걸 잡는 불변식이 없다**  |
| N1(위치 없음) → `0`으로 채움 | 계약 #2 §2-3 금지 사항. mAP가 인위적으로 낮아져 다섯 칸 비교가 통째로 무의미해진다 |

# 6. 경로 인계 규약: 수집 폴더(G:) ↔ 파이프라인(`data/raw/`)

## 6-1. 문제

`G:\공유 드라이브\대한산업공학회_추계학술대회\weld-fl-datasets\{dataset}\`로 직접 받고 **로컬 사본을 남기지 않는다.**
계약 #2의 `rel_path`는 **저장소 루트 기준 상대경로**(`data/raw/...`)이고 POSIX 슬래시이며
절대경로 저장이 금지다(`ImageRecord._posix`가 역슬래시를 거부한다).

## 6-2. 3층 분리

| 층 | 내용 | git |
|---|---|---|
| **논리층** (등록부) | `acquisition.staging_uri` = `"gdrive:weld-fl-datasets/RIAWELC"`, `pipeline.raw_subdir` = `"riawelc"`, `pipeline.dataset_subpath` = `"dataset/DB - Copy"` | 추적 |
| **물리층** (머신 로컬) | `configs/paths.local.yaml`. `staging_root` · `raw_root` · `rel_base` · `mount_mode` | **비추적** (불변조건 2-6. `.gitignore` 추가 필요. 미해결 사항) |
| **검증층** | `scripts/verify_landing.py`. 물리층이 논리층을 실제로 실현하는지 실측 | 추적 |

```yaml
# configs/paths.local.yaml   ← 커밋하지 않는다
staging_root: "G:/공유 드라이브/대한산업공학회_추계학술대회/weld-fl-datasets"
raw_root:     "E:/Fedvlm_for_welding_wt_A/data/raw"
rel_base:     "E:/Fedvlm_for_welding_wt_A"      # rel_path 기준 = 저장소 루트
mount_mode:   junction
```

**등록부에는 드라이브 절대경로가 들어가지 않는다.** 논리 URI만 적는다.

### `dataset_subpath`가 왜 필요한가: RIAWELC 실물

```
G:\공유 드라이브\대한산업공학회_추계학술대회\weld-fl-datasets\RIAWELC\
├── README.md
├── _archive\                              ← 원본 RAR 19파트
└── dataset\DB - Copy\
    ├── training\   {Difetto1, Difetto2, Difetto4, NoDifetto}
    ├── validation\ {Difetto1, Difetto2, Difetto4, NoDifetto}
    └── testing\    {Difetto1, Difetto2, Difetto4, NoDifetto}
```

현재 `RiawelcAdapter.discover()`는 `data/raw/riawelc/` **바로 아래 폴더 이름을 클래스로 읽는다.**
정션을 `RIAWELC\`에 걸면 라벨이 `_archive`·`dataset`이 되고, `DB - Copy`에 걸면
`training`·`validation`·`testing`이 된다. **둘 다 `unmapped_policy: fail`로 즉사한다.**

그래서 등록부가 두 값을 따로 받는다.

```json
"pipeline": { "raw_subdir": "riawelc", "dataset_subpath": "dataset/DB - Copy" },
"layout":   { "class_dir_depth": 2, "image_glob": "*.png", "label_mode": "dirname" }
```

`class_dir_depth: 2` = 이미지 폴더 위 2단계 중 **아래쪽**이 클래스다
(`training/Difetto1/*.png` → 클래스 `Difetto1`, 위쪽 `training`은 저자 분할이라 **버린다**).
어댑터의 2단계 순회 대응이 필요하다 (미해결 사항에 포함).

## 6-3. 잇는 방법: 정션. 단, 전제 3개를 먼저 확인한다

```
mklink /J "E:\Fedvlm_for_welding_wt_A\data\raw\riawelc" ^
          "G:\공유 드라이브\대한산업공학회_추계학술대회\weld-fl-datasets\RIAWELC\dataset\DB - Copy"
```

`resolve_image_path(rel_path, rel_base) = rel_base / rel_path` 이므로 정션을
`data/raw/<raw_subdir>`에 걸면 `rel_path`가 `data/raw/riawelc/training/Difetto1/x.png`가 되어
계약과 일치하고, 실물은 G:에 하나만 존재한다. **로컬 사본 없음 조건이 유지된다.**

**확인해야 할 전제 3개.**

1. **`data/raw`는 이미 정션이다.** 실측: `data/raw → E:\Fedvlm_for_welding\data\raw`,
   그 본체를 **worktree 5개가 공유한다.** 여기에 정션을 하나 더 만들면 A뿐 아니라 B·C·D·E에
   동시에 나타난다. 의도한 결과지만 되돌리는 절차를 dev_log에 남긴다.
2. **Google Drive 가상 드라이브에 `mklink /J`가 걸리는가.** 미검증. 거부되면 `mklink /D`로
   내려가는데, Python이 심볼릭 링크를 정션과 다르게 보므로 `rglob` 재귀 동작을 재검증해야 한다.
   둘 다 실패하면 로컬 반입(약 0.5~2 GB, E: 여유 226GB)으로 강등한다.
3. **처리량.** F 실측. 드라이브 동기화 폴더에 소파일을 쓰는 속도가 분당 약 500개다.
   sha256 전수 + 256bit pHash 전수는 1회면 되고(`phash.parquet` 캐시가 재실행을 구한다),
   `Image.open` 실패가 아니라 **시간**이 문제다. `acquisition.storage_mode: "drive_stream"`을
   경보 값으로 두고 시간을 예산에 넣는다.

### 금지: `--rel-base`로 우회하지 않는다

`scripts/run_pipeline.py`에 이미 `--rel-base` 플래그가 있다.
`--raw-root "G:/공유 드라이브/..."`를 넘기면 `rel_base = raw_root.parent.parent = "G:\"`가 되어
`rel_path`가 `공유 드라이브/대한산업공학회_추계학술대회/...`로 굳는다. `_posix`(역슬래시만 검사)를
그대로 통과하고, 불변식 어디에도 "`rel_path`가 `data/raw/`로 시작하는가" 검사가 없다.

`image_id = f"{source}:{rel_path}"` 이므로 이 한 번으로 PK 전체가 갈리고 잠긴 스냅샷과의
조인이 끊긴다. **`--rel-base`는 mock·픽스처 전용이다.** 강제 수단 신설은 미해결 사항.

## 6-4. 반출 제약 교차 검사: 검증기가 강제한다

```
provenance.export_restriction == "no_overseas_transfer"
  AND acquisition.staging_uri 가 "gdrive:" 로 시작        →  하드 실패
```

AI허브 71761은 **국외 반출 금지·내국인 한정**이고, Google Drive는 해외 호스팅에 리전 선택권이
없다. 8/16 회의의 "수집 데이터는 공유 Google Drive 적재"는 AI허브 승인 전에 정해진 것이고
그대로 적용할 수 없다. **논문의 서사가 "데이터를 밖으로 내보내지 않는다"인데 수집 단계에서
내보내면 전제가 스스로 무너진다.** 

저작권·보안 레드라인을 문서 리뷰가 아니라 **스크립트가 지키게 만드는** 지점이다.
공개 라이선스 데이터셋(RIAWELC·LoHi-WELD)은 이 규칙에 걸리지 않는다.

같은 방식으로 `kind=document`에도 건다.

```
document.paywalled == true  AND  document.index_inclusion == true   →  하드 실패
```

### 함정: 대괄호 파일명

RIAWELC 파일명이 `RRT-101R_Img1_A80_S1_[12][8].png` 형태다. 실측 확인:

```
glob.glob("RRT-101R_Img1_A80_S1_[12][8].png")   →  0건   ← [12] 가 문자 클래스로 해석된다
Path('.').glob(같은 이름)                        →  0건
Path('.').rglob("*.png")                        →  4,962건  ← 정상
```

`rglob("*.png")` 순회는 안전하지만, 파일명으로 직접 조회하는 코드나 셸 경유는 **예외 없이
조용히 0건**을 낸다. 어댑터·검증 스크립트에서 파일명 리터럴을 glob에 넣지 않는다.

### 함정: 한글 경로와 PowerShell 5.1

`G:\공유 드라이브`는 한글 + 공백이다. F 실측: UTF-8(BOM 없음) `.ps1`을 PowerShell 5.1이
ANSI로 읽어 `Illegal characters in path`로 죽는다. 처방은 F 보고서 7-2를 그대로 따른다 
경로를 코드포인트로 조립해 스크립트를 순수 ASCII로 유지하고, 네이티브 exe에 한글 경로를
인자로 넘기지 말고 `Set-Location -LiteralPath`로 이동한 뒤 상대 파일명만 넘긴다.

| **Notre Dame 95장** | 정체 규명 완료 (Khvatskii et al. 2025, *Information Fusion* 120:103121). 95장 이진 라벨 + 전문가 서술. **확보 실패 확정**. 공개 경로가 익명 심사 링크뿐이고 만료됐다(HTTP 410 `repository_expired`). 미러 없음. 등록부는 `access_state: unreachable` + `eligible: false`로 **닫는다.** 열린 채로 두면 8/25 게이트에서 다시 논의 비용이 든다 |

## 7-5. 갭이 알려주는 것

1. **두께·스케일은 어느 주 데이터셋에도 없거나 미확인이다.** 유일한 `present` 후보(Intel)는
   규모가 작고 비상업 한정이다. → `clause_only` 고정이 데이터 현실과 맞다.
2. **가시광 데이터셋 3개가 `modality` 값 공간 밖이다.** RT/VT 2값 설계가 RT 주 실험 전제에서
   나왔고, 확장 데이터셋이 전부 여기서 걸린다.
3. **계약 #1 L2에 온전히 사상되는 것은 AI허브와 RIAWELC 둘뿐이다.** 이건 결함이 아니라
   실험설계의 의도된 범위(주 실험 = RT 한정)와 정확히 일치한다. 등록부의 값은 **나머지를
   왜 안 쓰는지 문서로 방어**해 주는 데 있다. 심사에서 "왜 이 데이터셋은 안 썼나"에 답할 근거다.
4. **위치 라벨을 확정적으로 가진 것은 LoHi-WELD뿐이다.** AI허브는 설명서 근거(승인 후 확정),
   RIAWELC은 부재 확정.

**규칙 3개.**

1. **1 데이터셋 = 1 파일 = 1 담당자.** 남의 파일을 직접 고치지 않는다. 고칠 게 있으면 회의 안건.
2. **`dataset_id`를 회의 시트에서 먼저 예약한다.** `lohi_weld` vs `lohiweld` vs `lohi-weld` 처럼
   같은 데이터셋에 두 파일이 생기는 것이 가장 흔한 사고다. 검증기는 완전 중복만 잡고
   유사 ID는 못 잡는다. 여기는 사람이 막아야 한다.
3. **계약 파일은 A만 만진다.** 새 라벨 어휘는 자기 등록부의 `label_vocabulary.proposed_l2`에
   적고 A가 검토해 반영한다. 이것이 계약 #1 동결을 지키면서 팀원 작업을 막지 않는 유일한 경로다.

## 8-3. 데이터셋 1건 작성 순서 (40~90분)

```
①  _TEMPLATE_image.json 을 datasets/<dataset_id>.json 으로 복사
②  VS Code 로 연다. 첫 줄 "$schema" 덕분에 enum 이 드롭다운으로 나온다
③  provenance. 지금 받을 수 있는가부터 정한다
    access_state 가 unreachable/restricted 면 나머지를 unverified 로 두고 ⑨로 간다
④  provenance 나머지. 페이지·약관·논문을 열고 URL·판본·라이선스·인용을 옮긴다
    export_restriction 을 여기서 정한다 (④가 ⑤의 입력이다)
⑤  constraints ④에서 유도. 국외 반출·클라우드·상업 이용
⑥  acquisition / pipeline. 어디에 받았고, data/raw 아래 어느 이름으로 들어가는가
    아직 안 받았으면 access_state 만 적고 나머지는 unverified
⑦  layout / label_vocabulary. 압축을 풀어봤으면 실측, 안 풀었으면 unverified + evidence 에 "미열람"
    원본 라벨 문자열을 **그대로** 적는다 (번역·정규화 금지). proposed_l2 는 제안이다
⑧  fields_declared 10키. status + evidence + evidence_level. 여기가 본체
⑨  counts_announced (공지값 + basis + verified:false) / samples / open_items
⑩  uv run python scripts/validate_registry.py <파일>   → exit 0 또는 1 이 될 때까지
⑪  다른 사람에게 검토 요청 → authoring.review_status 는 검토자가 적는다
```

**③에서 막힌 데이터셋은 `fields_declared`를 통째로 생략한다.** KAMP·CMT·INWELD처럼
접근 경로 자체가 막힌 것에 10키 × `how_to_verify`·`owner`·`due`를 요구하면
채워질 방법이 "조사 필요" / "미정" 류 채움말뿐이다. 그건 이 설계가 막으려던 바로 그 날조이고,
동시에 8/23 헤드라인 수치를 무의미하게 부풀린다.
스키마가 `access_state ∈ {restricted, unreachable, not_requested}`일 때
`fields_declared`를 면제하고 `open_items`만 요구한다.

> **가장 중요한 한 줄: 추측해서 채우지 않는다.** 등록부의 값은 8/25 이후 실측과 대조되고,
> 대조가 어긋나면 분할 계획이 재작성된다. 추측으로 채운 칸은 그 대조를 무의미하게 만들고,
> 더 나쁘게는 **실측할 동기를 없앤다.**

## 8-5. 충돌 방지

| 표면 | 대책 |
|---|---|
| 같은 파일 동시 편집 | 1데이터셋=1파일 + `kind` 폴더 3분할 → 3인의 편집 표면이 **서로소** |
| `index.json` 재생성 diff | 기계 생성물. **충돌 시 병합하지 않고 재생성한다.** 재현 규격은 계약 #2 §6-9 승계. UTF-8 BOM 없음 / LF / `dataset_id` 오름차순 / `indent=2` / `ensure_ascii=false` / 키 순서 스키마 선언 순 |
| 저장소 커밋 권한 | `data/` 이하는 소관이고 팀원 2인은 브랜치 운용을 요구받지 않는다. **팀원은 공유 드라이브에 JSON을 올리고, A가 검증 통과분만 `wt/A`에 커밋한다.** git 충돌이 A 1인 손에서만 발생해 사실상 소멸한다 |
| 스냅샷 오염 | **등록부를 `SNAPSHOT.sha256`에 넣지 않는다.** 등록부는 계속 갱신되고 스냅샷은 확정 후 불변이다. `verify_snapshot()`이 멤버 목록 불일치를 하드 실패시키므로 넣으면 스냅샷이 매번 깨진다 |

### "작성 완료"의 정의

전 필드가 채워지는 것이 **아니다.**

> `validate_registry.py`가 **exit 0 또는 1**이고, 잔존 `unverified` 각각에
> `access_state` 또는 `how_to_verify`·`owner`·`due` 사유가 붙어 있는 것.

승인 대기 데이터셋을 억지로 채우게 만들면 추측이 확정으로 굳는다.
**`unverified`가 많은 파일은 성과다.** 이 문장을 회의에서 명시적으로 선언해야 한다 
스크립트로 막을 수 없는 유일한 실패 모드다.

"인덱스 완성" 같은 판정 불가 표현 대신 **네 숫자**로 보고한다.

present(full_scan/sample_inspected) 건수  ← 실제로 확인한 것
present(publisher_doc) 건수               ← 문서만 본 것
absent 건수                               ← 확인했고 없는 것
unverified 건수 (B등급 / D등급)           ← 남은 일
out_of_contract 건수                      ← 계약 확장 검토 대상
eligible=true 데이터셋 수 / 전체
```

## 9-1. 이 예시에서 눈여겨볼 것

| 지점 | 왜 이렇게 썼는가 |
|---|---|
| `eligible: false` + `adapter_state: "blocked"` | 실물이 있고 어댑터도 구현돼 있지만 **계약 #1 매핑이 어긋나 오늘 돌리면 즉사한다.** "등록부에 있다"와 "쓸 수 있다"가 다르다는 것을 이 두 줄이 보여준다 |
| `thickness_mm: absent` 의 `evidence` | "없는 것 같다"가 아니라 **"두께가 들어갈 파일 자체가 없다"**는 구조적 근거다. `evidence_level: full_scan`을 붙일 자격이 여기서 나온다 |
| `license.commercial_use` 만 `unverified` | D등급이라 ingest를 막지 않는다. B등급으로 뒀으면 "착수하려면 뭐라도 적어야 한다"는 압력이 생기고 그게 날조를 만든다 |
| `group_key.source: "filename_pattern"` | 메타데이터 필드는 없지만 묶음 ID가 파일명에 있다. 이 축이 없으면 정직한 기입이 `absent`가 되고, **누수 방어선이 통째로 끊긴다** |
| `counts_announced.verified: false` | F가 전수로 셌지만 그건 **드라이브 해제본 기준**이고, 우리 어댑터가 `data/raw` 경유로 세는 것과 대조돼야 확정이다 |
| `group_key` 정규식이 느슨한 이유 | ` - Copia` 접미 30건. **엄격하게 쓰면 그 30건이 각각 독립 묶음이 되어 누수가 난다.** 이 문서를 쓰면서 재실측으로 발견했고, 상류 문서(509)와 어긋난다 (§5-3) |
| `staging_uri: "gdrive:"` + `export_restriction: "none"` | RIAWELC은 공개 데이터셋이라 레드라인 교차 검사(§6-4)에 걸리지 않는다. **AI허브였다면 이 조합에서 하드 실패한다** |

# 10. 미해결 사항

이 설계로 처리할 수 없고 총괄 판정이 필요한 항목이다. **번호가 곧 우선순위다.**

### 1. 🔴 AI허브 71761을 Google Drive에 적재하는 것이 보안 레드라인 2-1과 충돌한다

`docs/개발규약.md` 불변조건 2-1은 "해외 호스팅 스토리지·해외 리전 클라우드에 원본이나
파생 이미지를 업로드하지 않는다"이고, 71761은 국외 반출 금지·내국인 한정이다. Google Drive는
해외 호스팅이며 리전 선택권이 없다. 8/16 회의의 "수집 데이터는 공유 Google Drive 적재"는
AI허브 확보 전에 정해진 값이다.

**현재 상태:** F는 RIAWELC·LoHi(둘 다 공개 라이선스)만 G:에 올렸고, AI허브는
`5deee13` 커밋 시점에 **사용자 직접 수령 대기**로 F의 수집 경로 밖에 있다. 그리고
승인 여부 자체가 미확인이다(F 5-4).

**결정 필요:** (a) AI허브는 국내 로컬 디스크(E:, 여유 226GB) 직수령 + 정션으로 인계,
(b) 나머지 공개 데이터셋은 Drive 허용. 승인 후에 옮기면 **이미 업로드된 것**이므로
승인 전에 정해야 한다. 등록부 스키마의 `if/then`으로 물리적으로 막을 준비는 해뒀다(§6-4).

### 2. 🔴 계약 #1 `sources.riawelc` 교체: 실물과 어긋나 있다

`configs/label_map.yaml`이 `"CR"/"PO"/"LP"` + `normal_labels: ["ND"]`인데 실제 폴더는
`Difetto1/Difetto2/Difetto4/NoDifetto`다. `unmapped_policy: fail`이므로 지금 ingest를
돌리면 즉사한다. 요청 사항 3가지.

1. `mapping`을 `Difetto1→crack / Difetto2→porosity / Difetto4→lack_of_penetration`,
   `normal_labels: ["NoDifetto"]`로 **교체**
2. `label_field`를 2단계 dirname으로 재정의 (경로가 `{split}/{class}/*.png`)
3. `RiawelcAdapter.discover()` 2단계 순회 + `_archive/` 제외 + 파일명 접두사 `group_id` 추출

이건 additive가 아니라 **교체**다. `version` 증가 여부와 함께 판정을 청한다.
관련: F 남은조치 3·4·5.

### 3. 🔴 `.gitignore`의 부활 패턴이 작동하지 않는다: 스냅샷 3종이 추적 밖이다

실측:

```
$ git check-ignore -v data/processed/foo_snap/manifest.csv
.gitignore:10:data/processed/    data/processed/foo_snap/manifest.csv
```

`data/processed/`가 디렉터리째 제외되면 `!data/**/manifest.csv` 부활 패턴은 **작동하지 않는다**
(git은 제외된 디렉터리 하위 파일을 다시 포함할 수 없다). `data/mock/`은 제외 목록에 없어서
mock만 추적되고 있고, 그래서 지금까지 아무도 눈치채지 못했다.

8/25 이후 실데이터 스냅샷을 만드는 순간 **논문에 싣겠다는 해시가 추적되지 않는 파일에만
존재한다.** 열린질문 Q7이 "잠금 = 해시 검증 + **git 추적**"으로 확정한 그 추적이 없다.
스냅샷 3종을 어디에 두어 추적할지(예: `data/snapshots/` 별도 경로) 결정이 필요하다.
