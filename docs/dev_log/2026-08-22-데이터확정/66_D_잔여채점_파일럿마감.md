## 4. 회복률 — 다섯 칸 기준

```
분리형  중앙 0.1904 · 연합 0.0623 · 로컬평균 0.0913 (C1 0.1203 / C2 0.1369 / C3 0.0166)
        분모 D = 0.0992 → 회복률 = −29.2%
통합형  중앙 0.2391 · 연합 0.1759 · 로컬 = 실험 구조상 '제외'
        회복률 정의의 분모(중앙−로컬)가 없다 → 유지율 73.5% 만 낸다
```

- **통합형에는 회복률이 없다.** 다섯 칸 설계에서 통합·로컬은 "제외" 칸이라 분모가
  존재하지 않는다. 유지율(연합/중앙)과 회복률은 다른 양이므로 한 표에 같은 이름으로
  싣지 않는다.
- **결론으로 쓰지 않는다** — 시드 1세트에 분모 0.0992 는 §5-4 규칙으로도 회복률을
  헤드라인으로 쓸 수 없는 구간이다(65번과 같은 문구).
- 0절을 고려하면 통합형의 유지율 73.5% 는 "연합이 중앙의 4분의 3을 유지했다"가 아니라
  **"연합 쪽이 지름길을 덜 강하게 배웠다"**로도 똑같이 설명된다(발화율 0.915 → 0.647).
  파일럿 수치로 두 해석을 가를 수 없다.

| 임베더 호출 횟수 | **0** (호출 시 예외를 던지는 임베더로 확인) |
| 정답 조항 순위 분포 | {1위: 100} |
| 동점 수 | 0 |
| top-1 / top-3 | 1.000 / 1.000 — **어느 모델이든 같다** |
| 본문이 빈 청크 | **4 / 4** |

**두 후보를 내려받지 않았고, 그것이 이번 측정의 결과다.** 이유가 둘이고 각각 단독으로
비교를 무너뜨린다.

1. **임베딩 경로에 진입하는 질의가 0건이다.** `retrieve()` 는 후보가 2개 이상일 때만
   dense 정렬을 부른다. 100건 전부 구조화 lookup 이 후보를 1개로 확정하므로
   BGE-M3 와 Qwen3-Embedding-4B 의 출력은 **정의상 비트 단위로 같다.** 실행해도 둘 다
   top-1 = 1.000 이 나오며, 그 1.000 은 임베딩 성능이 아니라 lookup 의 성능이다.
2. **색인에 조항 본문이 없다.** 4개 청크 전부 `text` 길이 0이다 —
   `corpus/derived/chunk_meta.jsonl` 은 메타데이터만 담고 본문 필드가 없다. dense 정렬이
   걸리더라도 정렬할 재료가 없다(빈 문자열 4개는 서로 구별되지 않는다).

지시의 "포화되면 변별 불가로 보고하고 모델을 고르지 마라"에 정확히 해당한다.
`configs/rag.yaml` `embedding.model` 은 **null 로 둔다** — 미선정 상태에서 dense 정렬이
필요해지면 코드가 사전순 폴백으로 조용히 넘기지 않고 `MissingEmbeddingModel` 로 죽는다.

재개 조건: **B 가 조항 본문을 파생물에 실어야 한다.** 본문이 들어오고 청크가 늘어
후보 복수 질의가 생기면 같은 스크립트(`scripts/probe/embedding_decision.py`)가 그대로
실측으로 전환된다. 그 전까지 의사결정로그의 이 항목은 미정으로 남는다.

**격리 위반이 아닌 근거**(지시대로 남긴다): `13_spec_D` §5-4 가 "gold_clauses.csv 에서
질의 100건 추출 → 후보별 top-1 측정 → 채택 후 고정"을 임베딩 선정 절차로 **사전 등록**
했고, 의사결정로그 미정 항목이 같은 절차를 가리킨다. 격리(불변조건 1-4)가 금지하는 것은
평가 자산의 **학습 투입**이며, 이 사용은 학습이 아니라 검색기 구성요소의 사전 등록된
선정 절차다. 한국어 평가셋 599행은 이 절차에 관여하지 않았다.

## 8. `max_new_tokens` 재산정 — 실측식

토크나이저는 `Qwen/Qwen3.5-0.8B` 실물. C 의 성공 생성문 1,270건을 세었다.

**통합형 출력 토큰 = 26 + 30 × (결함 수)** (결함 0개일 때 20)

| 결함 수 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 최대 토큰 | 20 | 56 | 86 | 116 | 146 | 176 | 206 | 236 |

식의 검증: 256 토큰은 결함 **7.6개**에서 소진된다. C 가 보고한 절단 건이 "전부 결함
8~9개 이미지"였던 것과 정확히 맞는다(고장 7 의 원인 규명 완료).

**지시서의 전제를 정정한다. 이미지당 최대 결함 수는 9개가 아니라 31개다.**

| 기준 | 최대 결함 | 필요 토큰 | ×1.5 여유 | 권고 |
|---|---|---|---|---|
| 파일럿 표본 전체(3,279장) | **31** | 982 | 1,473 | **1,536** |
| 파일럿 평가셋(653장)만 | 24 | 762 | 1,143 | 1,216 |
| 지시서 전제(관측 9) | 9 | 296 | 444 | 512 |

표본에 결함 8개 이상 이미지가 **132장(4.0%)** 있고, 평가셋에서의 절단율 4.90% 와
같은 자릿수다. 9개로 잡으면 다시 절단된다.

- **통합형 권고: `MAX_NEW_TOKENS = 1536`** (`scripts/pilot_export_vlm.py`, C 소유 파일이라
  D 가 고치지 않았다). 평균 비용은 거의 오르지 않는다 — greedy 는 EOS 에서 멈추고,
  긴 예산을 실제로 쓰는 것은 다결함 이미지뿐이다. 최악 지연만 늘어난다.
- **판정부 권고: 512 유지** (`configs/rag.yaml` `judge.max_new_tokens`). 판정부 출력은
  결함 수에 비례하지 않는다(`{verdict, cited_clauses, basis}` 고정 구조). 최악 형태
  (조항 3건 인용 + 긴 한국어 기준 문장)를 직접 세어 **149 토큰**, 512 는 3.4배 여유다.
  값은 그대로지만 이제 관례가 아니라 실측이다.
- **본실험 착수 조건**: 결함 수 상한은 파일럿 3,279장의 관측치다. 70,000장의 상한을
  A 가 전수로 내고, 그 값으로 `26 + 30×N` 을 다시 평가해야 한다.

## 9. ⑤ 판정부 실행

`configs/rag.yaml` `judge.checkpoint: "Qwen/Qwen3.5-0.8B"` 기재 완료 (C 확정값, 61번 §0).
**어댑터는 붙이지 않았다** — ⑥의 어댑터는 이미지→JSON 과업으로 학습됐고 판정부는 텍스트
과업이다. 개발규약이 공통 고정하는 것은 "기본 모델 체크포인트"이며, 판정부 SFT 는
파일럿 범위 밖이라 기본 가중치로 돌았다. bfloat16, greedy 1회.

### 9-1. 주 실행 (사전등록 그대로) — **전 건 `해당 조항 없음`**

분리형 5모델 × 653장 = 3,265건.

| 칸 | 이미지 | 질의 (이미지×결함코드) | 검색 적중 | 생성 호출 | 무검색 경로 |
|---|---|---|---|---|---|
| 분리·중앙 | 653 | 84 | **0** | **0** | 653 |
| 분리·로컬 C1 | 653 | 91 | 0 | 0 | 653 |
| 분리·로컬 C2 | 653 | 133 | 0 | 0 | 653 |
| 분리·로컬 C3 | 653 | 11 | 0 | 0 | 653 |
| 분리·연합 | 653 | 49 | 0 | 0 | 653 |

**정답 조항 쌍도 0건이다** — GT 결함 쌍 388건 전부 `정답 조항 없음` 으로 조회 실패.

원인은 하나다. **두께가 없다.** 스냅샷 실측에서 `thickness_mm` 비결측 0건,
`thickness_source: none`, `px_per_mm` 비결측 0건이다. 허용치 표의 조항은 전부 두께
구간 `[min, max)` 을 가지므로, 두께가 `None` 이면 `_thickness_matches` 도
`GoldEntry.covers_thickness` 도 False 를 돌려준다. 검색도 정답도 성립하지 않는다.

- **지시 항목 "검색 0건 시 `해당 조항 없음` 경로가 실제로 타는지 확인" → 확인됐다.**
  3,265건 전부 그 경로다. 생성 호출 0회이므로 규약(검색 0건이면 모델에게 묻지 않는다)이
  코드로 지켜졌고, 시험이 아니라 실물에서 확인됐다.
- **그리고 그것이 차단이다.** 판정 근거 신뢰도 축(조항 정확도·인용 정합)은 **파일럿 자산
  으로 산출 불가**다. 이것이 함정 #10(픽셀→mm 변환)이 평가 쪽에서 발현한 형태다.
- 기계 기록에는 `clause_top1 = 0.0`, `citation_match_rate = 0.0` 이 남지만 **이 값을
  0으로 읽지 않는다.** 분모(정답 쌍)가 0이라 정의되지 않는 것이고, 결과표에는 `N/A` 로
  올린다. 13_spec_D §5-6 의 `clause_only` 규약("판정 정합성 N/A, 조항 검색·인용 일치율은
  정상 산출")도 두께가 있을 때를 전제한 것이라, 지금은 세 지표가 전부 N/A 다.
- 우회하지 않았다. 가정 두께를 채워 넣으면 숫자는 나오지만 그 숫자는 데이터가 아니라
  우리 가정의 함수이고, `verdict_mode: conditional` 승격은 총괄 승인 사항이다.

### 9-2. 생성부 시운전 (배관 검증 — 지표 아님)

주 실행이 생성을 한 번도 부르지 않으므로 생성부가 도는지는 따로 확인해야 한다.
**새 가정을 도입하지 않기 위해**, 검색이 실제로 걸리는 입력으로 사전 등록된 임베딩 실측
질의 100건(§7)을 그대로 재사용했다 — 이 질의의 두께는 허용치 표 **자신의 구간**에서
나온 값이라 가정값이 아니다. 아래 수치는 **배관·인용 접지 진단이며 판정 근거 신뢰도
지표가 아니다.** 결과표에 싣지 않는다.

프롬프트 sha256 `318945658f49e673f8515e934769756def5f797fe252629d981a1b2f3d1b5724`
· `Qwen/Qwen3.5-0.8B` bf16 · greedy 1회 · `max_new_tokens` 512 · 422초(질의당 4.3초)

| 항목 | 값 | 읽는 법 |
|---|---|---|
| 생성 호출 | 100 (= 검색 적중 질의 수) | **재시도 0회.** 코드가 호출 수를 직접 세고 시험이 고정한다 |
| 파싱 실패율 | **0.0000** | 스키마 위반 0. JSON 추출·enum·목록형 전부 통과 |
| verdict 분포 | `판정불가` 100 | clause_only 축의 정합값. 합부를 낸 건 0건 — 프롬프트 규칙 준수 |
| 인용 건수 | 100 | 질의당 1건 |
| 색인에 없는 조항 인용 | **0** | **지어낸 조항 없음** |
| 제시 밖 조항 인용 | **0** | 제시된 것만 인용했다 |
| 정답 조항 인용 | 100/100 | **구조적으로 자명하다** — 후보가 1개뿐이라 베끼면 맞는다 |
| 출력 토큰 | 중앙값 78 · 최대 79 | §8 의 최악 추정 149의 절반. 512 예산은 넉넉하다 |

**숫자가 좋아 보이지만 읽을 것은 두 가지다.**

1. **`basis`(기준 서술)가 비어 있다.** 100건의 근거 문장이 서로 다른 것이 **5가지뿐**이고,
   전부 `"KRA27-T16 는 본문 미등재 조항으로, …"` 로 시작한다. §7 에서 본 대로 색인에
   조항 본문이 없어 프롬프트의 조항 자리에 `(본문 미등재)` 만 들어가기 때문이다.
   **인용은 접지됐지만 서술할 기준이 없다** — 판정 축의 절반이 재료 부재로 비어 있다.
2. **프롬프트 문장이 출력으로 새어 나온다.** 100건 중 일부(예: 질의099)의 `basis` 가
   `"KRA27-3D 는 본문 미등재 조항으로, 제시된 조항 외의 조항 번호를 만들어내지
   마십시오."` 다 — 지시문을 근거 문장 자리에 그대로 옮겼다. 판정부 SFT 없이 기본
   가중치 0.8B 로 돌린 결과이며, 본실험에서 판정부 SFT(D3 판정추론 corpus)가 왜 필요한지의
   실측 근거다.

시운전 중 발견해 고친 것: `build_prompt` 가 `size_px` 가 `None` 일 때 `미상` 이 아니라
문자열 `None` 을 프롬프트에 실었다(`dict.get(key, 기본값)` 은 키가 있고 값이 `None` 이면
`None` 을 돌려준다). 모델이 그 `None` 을 근거 문장에 그대로 옮기는 것을 첫 실행에서
확인하고 고친 뒤 전량 재실행했다. 위 수치는 재실행분이다. 회귀 시험 1건 추가.

## 10-b. 하지 않은 것 — 라운드별 궤적 채점

지시서가 "라운드별 글로벌 체크포인트(검출 3벌·VLM 3벌)로 RQ3 궤적 채점 **가능**"이라고
알려줬으나 이번에는 하지 않았다. 궤적은 같은 지표를 라운드축으로 늘어놓는 것인데,
§0 에서 그 지표가 출처 축에 지배된다는 것이 나왔다. 지금 궤적을 그리면 "라운드가 갈수록
지름길을 얼마나 배웠는가"를 회복 곡선으로 잘못 읽게 된다. **크롭 한정본 승격 판정
(§12-1) 뒤에 하는 것이 맞다.** 체크포인트는 그대로 남아 있어 언제든 돌릴 수 있다.

## 12. 총괄에 올리는 결정 항목

1. **크롭 한정본 승격 여부** (§0). 57번 사전 등록 분기의 "쏠린다" 쪽이 실측으로 나왔다.
   승격 시 A 의 분할 재작성 + 다섯 칸 재실행.
2. **출처 전용 기준선을 `configs/base.yaml` 사전등록 블록에 추가**할지 (§0-3, §5).
3. **`verdict_mode` 를 `conditional` 로 승격할지** (§9-1). 승격하지 않으면 판정 근거
   신뢰도 축은 본실험에서도 산출되지 않는다. 승격하면 가정값 3종을 B·D 가 같은 키로
   읽는 G14 인터페이스를 먼저 세워야 한다.
4. **B 에 조항 본문 파생을 요청**할지 (§7, §10-7). 임베딩 선정과 판정부 기준 서술이
   둘 다 여기서 막혀 있다.
5. **C 에 `MAX_NEW_TOKENS = 1536` 반영 요청** (§8). D 가 남의 트랙 파일을 고치지 않았다.
6. **mAP 를 RQ2(구조 비교) 축에서 뺄지** (§1, §10-8). 통합형은 신뢰도를 내지 않아 순위가
   없고, 그 비대칭이 IoU 성능과 무관하게 mAP 를 3배 갈라놓는다. 결함 놓침·Class-Jaccard·
   BBox-IoU 는 순위에 의존하지 않으므로 구조 간 비교축으로 그대로 쓸 수 있다.
