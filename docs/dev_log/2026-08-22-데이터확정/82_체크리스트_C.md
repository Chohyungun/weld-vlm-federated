## 2. 판정 2 — FedAvg 가중을 감독 토큰 총합으로

`fl/client_vlm.py` 가 `WEIGHT_KEY` 에 `supervised_tokens` 를 싣는다. 페어 수는 버리지 않고
`num-examples` 로 함께 올린다.

**왜 같은 단위여야 하는가.** 손실 정규화가 감독 토큰 총합 분모이므로(§4), 가중도 같은
단위여야 연합 목적함수가 중앙(합동 학습)의 목적함수와 일치한다 — `R × E = N` 등가 주장의
실질이 그것이다. 페어 수로 가중하면 토큰 밀도 차(c0 192.1 / c1 105.3 / c2 100.8 tok/페어)가
목적함수를 비튼다.

### 2-1. 회계가 단위를 말한다

`AccountingCell` 에 세 필드를 넣었다.

| 필드 | 뜻 |
|---|---|
| `fedavg_weight` | 집계가 **실제로 쓴** 가중 |
| `fedavg_weight_unit` | `"supervised_tokens"`(통합형) / `"num_examples"`(검출) |
| `supervised_tokens` | 감독 토큰 총합. 통합형에선 가중 그 자체다 |

가중 단위가 바뀌면 C3 비중이 1.52배 움직이고 **RQ3 이 그 위에 선다.** 어느 단위로 잰
값인지 산출물이 말하지 않으면 나중에 해석할 수 없다.

회계 감사에 검사 두 개를 더했다 — 한 run 안에서 **단위가 갈리면 실패**(두 목적함수를 섞은
것이다), **가중이 0 이하인 셀이 있으면 실패**(그 클라이언트의 학습이 집계에 반영되지 않았다).

원자 로그에도 `supervised_tokens`·`fedavg_weight` 를 남긴다. F9 가 지적한 것 —
⑦ 로그에 `epochs_ran`·`lr` 이 없어 `R×E=N` 을 복원할 수 없었고, 그래서 회계가 상수로
채워질 수밖에 없었다 — 도 함께 닫았다.

## 3. 판정 4 — 통합형 LR 전역 오프셋 cosine

`vlm/schedule.py` 신설. 검출이 쓰는 `one_cycle` 코사인을 **같은 식으로** 옮겼다.

    lr(x) = lr0 × [ ((1 − cos(π·x)) / 2) × (lrf − 1) + 1 ],   x = 전역 진행률

**스텝 단위로 잇는다.** 명세 문장이 "각 클라이언트 총 스텝 예산 전체에 걸친 단일 cosine 을
전역 스텝 오프셋으로 이어 간다"이고, epoch 으로 이으면 클라이언트마다 epoch당 스텝이 달라
궤적이 갈린다. `train_rounds` 가 `num_rounds` 를 받아 `총 스텝 예산 = R × 라운드당 스텝` 을
만든다 — 여기에 라운드 길이를 넣으면 라운드마다 리셋돼 다시 어긋나고, 시험이 그 톱니를
이빨로 쓴다.

`metrics` 에 `lr0`·`lrf`·`lr_trace_head/tail`·`steps_per_round`·`total_step_budget` 을
싣는다. 회계 CSV 의 `lr` 이 9행 전부 0.0001 이던 상태(F12)가 이걸로 끝난다.

### 3-1. 판정 요청 — warmup 비대칭 1건

검출 `FIXED_OVERRIDES` 는 `warmup_epochs: 3.0` 을 쓴다. 총괄 판정 4 의 문언은
"전역 오프셋 cosine" 이고 warmup 언급이 없다.

**임의로 넣지 않았다.** warmup 은 학습 궤적을 바꾸는 5칸 공통 고정 변경이고, 트랙이 단독으로
할 일이 아니다. `warmup_steps` 인자만 열어 두고 기본값 0 으로 뒀다. **두 칸을 완전히 대칭으로
맞추려면 warmup 도 함께 확정해야 한다** — 판정 요청으로 올린다.

## 4. 항목 5 — 손실 정규화 (`vlm/loss_norm.py`)

### 4-1. 무엇이 틀렸었나

선언은 토큰 균일(`Σce_i / Σn_i`)인데 코드는 샘플마다 `(ce_i/n_i).backward()` 를 해서
실제 목적함수가 샘플 균일(`Σ(ce_i/n_i)`)이었다. 감독 토큰이 19~947 로 **49.8배** 퍼져
있어 토큰당 기울기 가중이 median 17.1배 갈렸고, 방향이 하필 나쁘다 — **결함 0건 답의
토큰이 결함 보유 답보다 6.13배 무겁다.** 짧은 답이 "결함 배열을 비우는 쪽"이라 헤드라인인
결함 놓침 비율에 직결된다.

### 4-2. 창 전체를 미리 세지 않고 기울기를 나눈다

`Σn_i` 는 backward 시점에 아직 모르는 값이다. 세 길을 놓고 골랐다.

| 안 | 문제 |
|---|---|
| 창 32개를 미리 인코딩해 `n_i` 를 모은다 | 970 패치짜리 비전 입력 32벌을 들고 있어야 한다 — VRAM 예산(판정 10)을 깬다 |
| 텍스트만 미리 토크나이즈 | `prompt_len` 이 이미지 토큰 수에 걸려 있어 정확히 셀 수 없다. 근사하면 그 근사가 새 오차다 |
| **누적한 기울기를 창 끝에서 한 번 나눈다** | 없다. `Σ∇ce_i / D == ∇(Σce_i / D)` — 미분은 선형이다 |

셋째를 골랐다. 추가 메모리 0, 근사 0. 그래서 이 모듈이 파는 것은 손실 함수가 아니라
**누적 창 규약**이다 — `ce_sum` 을 그대로 backward 하고, 창이 닫힐 때 `rescale_grads_` 로
나눈 뒤 step 한다.

### 4-3. 시험 8건 — 지시서가 요구한 3종 + 이빨

| 시험 | 무엇 |
|---|---|
| 기준경로 1e-5 | `supervised_ce_sum / n` vs `F.cross_entropy(reduction="mean")` |
| 라벨 밀림 검출 | 한 칸 밀면 값이 1.0 이상 달라진다. shift 지점이 하나여야 한다는 규약의 이빨 |
| **길이 19 대 947 혼합 누적** | 누적-후-나누기가 단일 큰 배치와 1e-5 이내 |
| **구코드 샘플균일 누적은 실패한다** | *지시서가 "현 코드에서 반드시 실패해야 한다"고 지목한 그 비교*. 옛 규약으로 같은 창을 돌리면 기울기 스케일 비가 2배를 넘는다 |
| 정본 우회 금지 | 학습 루프가 `cross_entropy` 를 직접 부르면 AST 시험이 실패 |

셋째 시험만 있으면 "통과하는 시험"일 뿐 무엇을 잡는지 말하지 못한다. 넷째가 그것을 말한다.

## 5. 항목 14 — 본실험 Flower 진입점

### 5-1. 세 고장이 전부 "배선이 두 벌이라서" 났다

`fl/server_app.py`(`flwr run`)와 `fl/pilot_sim.py`(`run_simulation`)가 라운드 종료 기록과
회계 마감을 **각자** 구현하고 있었다.

| 고장 | 어느 쪽 |
|---|---|
| 회계 마감이 `finally` 가 아니라 평문 호출 — 학습 밖 단계가 죽으면 회계 유실 | server_app 만 |
| `audit.json` 미기록 | server_app 만 |
| 라운드 키가 `"round"` 대 `"server-round"` → 라운드 1 에서 `KeyError` | 두 벌이 달랐다 |
| `_load_initial` 이 `NotImplementedError` | server_app |
| `[tool.flwr]` 부재 → `flwr run` 이 앱을 **해석조차 못 함** | pyproject |

공통부를 `fl/round_wiring.py` 하나로 내리고 두 진입점이 그것만 부른다(G10-2).
`SERVER_ROUND_KEY`·`CANONICAL_KEYS_KEY` 는 상수로만 참조하며, **리터럴 사용을 시험이 금지**한다.

`_load_initial` 은 두 칸 모두 구현했다 — 검출은 `detection/init_weights`, 통합형은
`vlm/init_adapter`. F11(캐시 분기가 `ref` 를 빈 dict 으로 돌려주는 문제)도 함께 닫았다.

### 5-2. 스모크는 코드 안의 경로여야 했다

처음에는 시험에서 `monkeypatch` 로 클라이언트를 더미로 바꾸려 했다. **안 된다** — Ray 액터는
별도 프로세스라 부모의 패치가 닿지 않는다. 실물 클라이언트가 그대로 돌아 GPU 를 잡았고,
`num_gpus=0` 을 주니 `Invalid device id` 로 죽었다.

그래서 배선에 `SMOKE_CELL` 을 **1급으로** 뒀다(G10-2 가 말한 "더미 2텐서" 그대로).
오용 방지로 이 칸의 산출물 디렉터리에는 `DO_NOT_CITE.md` 가 함께 쓰인다.

`SMOKE_BACKEND`(GPU 0) 도 함께 뒀다. 배선을 보는 시험이 GPU 를 요구하면 (가) CPU 전용
러너에서 못 돌고 (나) 같은 기계의 학습과 경합해 굶는다 — 실제로 10분 넘게 굶었다.

### 5-3. 스모크 4종이 실제 런타임 위에서 돈다

R=2 · E=1 · 클라이언트 3 · 더미 2텐서.

- **완주** — `audit.ok`, `accounting.csv`·`atomic_log.csv`·`global_r002.npz` 생성,
  클라이언트별 총 epoch 이 정확히 N
- **가중 단위 기록** — 회계 CSV 의 `fedavg_weight_unit` 이 전 행 `supervised_tokens`
- **원자 로그 필수 지표** — `epochs_ran`·`lr`·`supervised_tokens`·`fedavg_weight` 존재(F9)
- **클라이언트 kill** — r1c2 를 죽이면 예외가 나되 **`audit.json` 이 디스크에 남고
  `ok=false` 에 실패 사유가 적힌다.** `finally` 가 값을 하는지를 이 시험이 판정한다

## 6. 항목 15 — ⑦을 Flower 로

`cmd_cell7` 의 인프로세스 순차 루프를 지우고 `run_pilot_fed(cell="uni_fed")` 로 바꿨다.

**우회가 무엇이었나.** 전송 계층을 건너뛰었으므로 전략의 실패 검사 셋(에러 응답 · 응답 수
대조 · 키 다이제스트)이 **한 번도 발화하지 않았고**, 회계가 실패해도 예외를 올리지 않고
`audit.json` 도 쓰지 않았다 — `sep_fed/audit.json` 은 있는데 `uni_fed/` 에는 없었다(F6).

이제 두 연합 칸이 같은 `WeldFedAvg` 를 탄다. 칸 분기는 **초기 파라미터와 클라이언트 함수
선택**에만 있다. `fl/client_vlm.py` 는 `run_client_round` 를 순수 함수로 두고
`@app.train()` 은 자료형 변환만 하는, 검출 클라이언트와 같은 모양으로 짰다.

어댑터 교환 규약(`adapter_exchange_contract`)은 그대로이고, 바뀐 것은 그 함수들을 **누가
부르는가**뿐이다. 오히려 인프로세스 루프에서는 안 돌던 실패 검사가 이제 돈다.

| 게이트 레지스트리 `evaluation/gates.py` + `verify_against_prereg`·`recovery_denominator_ok`·`guard_no_cloud_logging`·`require_tags` 배선 | **D** | 18항의 D 몫. C 는 `deterministic_torch`·`check_cells_identical` 둘만 배선했다 |

### 10-3-1. **본실험 착수 차단 — D 채점 경로가 본실험 규모에서 돌지 않는다**

§4-6 게이트를 돌리면서 드러났다. 셋 다 **파일럿 규모(653장·YOLO11n·416)에서는 안 보이다가
본실험 규모에서 죽는다.** 80번이 말한 "경로를 한 번도 안 돌려 봐서 나는 사고"와 같은 형태다.

| # | 결함 | 실측 | 영향 |
|---|---|---|---|
| 1 | `evaluation/detect_infer.load_yolo_from_npz` 가 `cfg="yolo11n.yaml"` **하드코딩** | `SerializeError: shape 불일치 [model.0.conv.weight]: (32,3,3,3) != (16,3,3,3)` | 본실험 프로파일(YOLO11s) 가중치를 **읽지 못한다.** 다섯 칸 중 어느 것도 본실험 프로파일로 채점 불가 |
| 2 | `predict_cell` 이 청킹 없이 전량 추론 | `DefaultCPUAllocator: not enough memory: you tried to allocate 36748984320 bytes` (36.7GB) | 평가셋 12,461장에서 **단일 할당 요구**라 어떤 기계에서도 안 된다 |
| 3 | `ScoringParams.IMGSZ = 416` (파일럿 값) | — | 640 으로 학습한 모델을 416 으로 추론하면 그 차이가 판정 오차가 된다 |

**`evaluation/` 는 D 소관이라 고치지 않았다.** 게이트 스크립트에서 1은 cfg 만 바꾼 같은
절차로, 2는 같은 함수를 256장씩 나눠 부르는 것으로, 3은 `imgsz=640` 명시로 우회했다.
**추론(`predict_cell`)·채점(`score_detection`·`cluster_bootstrap`)은 전부 D 것을 그대로
부른다** — 두 번째 채점기를 만들지 않았다.

D 가 본실험 전에 (1) `load_yolo_from_npz` 에 모델 cfg 를 인자로 열고 (2) `predict_cell`
안에 청킹을 넣고 (3) `IMGSZ` 를 프로파일에서 받아야 한다.

### 10-4. 작업 중 마주친 것 — 기록

- **§4-6 학습을 두 번 돌렸다.** 첫 런(33 epoch, 59.8분)이 완주했는데 **가중치가 디스크에
  없었다.** `save: False` 가 다섯 칸 공통 고정(best 체크포인트 금지의 이행)이라 Ultralytics
  가 아무것도 안 남기고, `RoundResult.ndarrays` 를 호출부가 저장해야 한다 —
  `cmd_train` 이 그걸 안 했다. `detection/train_cell.save_cell_weights` 로 고치고
  재실행했다. 시드·cudnn 결정론이 고정돼 있어 재현되는 런이다.
- **같은 기계에서 B 의 corpus 재생성(체크리스트 19)이 동시에 돌아** 시스템 커밋 여유가
  0.5GB 까지 떨어졌다(B 20GB + 이쪽 학습 14GB). 시험 수집이 `_ssl` DLL 로드 실패로 죽는
  현상이 났다. **B 의 작업은 건드리지 않았고** 전체 시험은 학습 완료 후 돌렸다.
- 스모크가 GPU 자원을 요구해 게이트 학습과 경합하며 10분 넘게 굶었다. `SMOKE_BACKEND`
  (GPU 0)를 둔 계기다 — CI 러너에 GPU 가 없어도 돌아야 한다.
