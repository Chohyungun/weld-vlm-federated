# FL 앱 계층 설계 — 트랙 C

2026-08-23 · `wt/C` · 착수 전 설계 · 구현은 게이트 통과 후

`fl/`의 빈 자리 셋(`server_app.py`·`client_det.py`·`client_vlm.py`)을 채우는 설계다.
아래층 네 모듈(`round_runner`·`serialize`·`fed_trainer`·`aggregate`)은 이미 있고 테스트를
통과한 상태이므로, 이 계층은 **그것들을 Flower 실행 모형에 접합하는 얇은 배선**이어야 한다.
계층이 두꺼워지면 우리가 막아 둔 기본값이 되살아날 자리가 생긴다.

---

## 1. Flower API 확정 — **Message API 채택** (실측 근거)

설치된 `flwr 1.33.0`을 직접 찍어 확인했다. 추측하지 않았다.

### 1-1. 두 API가 공존한다

| | 레거시 | Message |
|---|---|---|
| 전략 경로 | `flwr.server.strategy.FedAvg` | `flwr.serverapp.strategy.FedAvg` |
| 훅 이름 | `configure_fit` · `aggregate_fit` | `configure_train` · `aggregate_train` |
| 클라이언트 선택 인자 | `fraction_fit` · `min_fit_clients` · `min_available_clients` | `fraction_train` · `min_train_nodes` · `min_available_nodes` |
| `accept_failures` | **있음** (`= True` 기본, L109) | **없음** |
| 교환 자료형 | `Parameters` · `FitRes` | `ArrayRecord` · `MetricRecord` |
| 실행 | `ServerApp(server_fn=...)` → `ServerAppComponents` | `@app.main()` + `Strategy.start(grid, ...)` |

**`ServerApp`과 `ClientApp` 클래스 자체는 하나다** — `flwr.serverapp.ServerApp is
flwr.server.ServerApp` → `True`. 두 스타일을 같은 클래스가 지원하며, 레거시 스타일은
생성자 인자(`server_fn` / `client_fn`)로, Message 스타일은 데코레이터(`@app.main()`,
`@app.train()`)로 갈린다.

### 1-2. Message API의 실패 처리 — 소스로 확인

```python
# flwr/serverapp/strategy/fedavg.py  aggregate_train
valid_replies, _ = self._check_and_log_replies(replies, is_train=True)
arrays, metrics = None, None
if valid_replies:
    arrays = aggregate_arrayrecords(reply_contents, self.weighted_by_key)
```

`_check_and_log_replies`(L188~)는 `msg.has_error()`로 응답을 갈라 **에러 쪽은 로그만 남기고
버린다.** 그리고 집계는 살아남은 응답만으로 진행된다.

```python
# strategy_utils.aggregate_arrayrecords
total_weight = sum(weights)
weight_factors = [w / total_weight for w in weights]
```

가중치가 **살아남은 클라이언트끼리 다시 1로 정규화된다.** 즉 C3가 라운드 30에서 죽어도
C1·C2 가중치가 32:16에서 2:1로 재정규화되어 집계가 성립하고, 라운드는 정상 종료하며,
지표는 초록이다. **`R × E = N`만 조용히 깨진다.** 게이트 #6 결정 A가 막으려던 바로 그 경로가
Message API에서는 파라미터로 막을 수단이 없다.

레거시는 `accept_failures=False`(L229·L265 `if not self.accept_failures and failures:`)로
집계를 건너뛸 수 있다.

### 1-3. 그런데도 Message API를 택한다 — 근거 넷

1. **레거시는 공식 호환 레이어다.** 레거시 `ServerApp(server_fn=...)`의 반환형이
   `flwr.compat.server.serverapp_components.ServerAppComponents`다. 이름이 `compat`이다.
   새 코드를 호환 레이어 위에 짓는 것은 처음부터 부채를 지는 선택이다.
2. **시뮬레이션 진입점이 Message 기준이다.** `run_simulation(server_app, client_app,
   num_supernodes, backend_name='ray', backend_config=...)`이 우리 실행 형태(1 GPU Ray
   시뮬레이션)의 정본 경로다.
3. **레거시의 `accept_failures=False`도 우리 요구를 만족하지 못한다.** 그것은 "실패가 있으면
   집계를 건너뛴다"이지 "라운드를 중단하고 run을 무효로 만든다"가 아니다. 우리 요구는
   회계 매트릭스의 빈 셀을 실패로 정의하는 것(게이트 #6 결정 A)이므로 **어느 API를 택해도
   커스텀 검사가 필요하다.** 그렇다면 현행 API 위에 얹는 편이 낫다.
4. **30번 명세 판정 14가 같은 방향이다** — "라운드 실패 방어: `accept_failures=False` vs
   **전략이 직접 검사**".

**결론: Message API + `FedAvg` 서브클래스에서 실패를 직접 검사한다.**

## 2. 모듈 구조

```
fl/
├── __init__.py        ✅ (비어 있음 — 유지)
├── aggregate.py       ✅ 검출 집계: 표본수 가중 FedAvg + BN buffer 정책 (함정 #2)
├── strategy.py        ➕ WeldFedAvg — Message FedAvg 서브클래스. 실패 차단 + 회계 적재
├── server_app.py      ➕ ServerApp 1벌. cell 로 검출/VLM 분기
├── client_det.py      ➕ 검출 ClientApp
└── client_vlm.py      ➕ VLM ClientApp (골격만. 본체는 분리형 3칸 완주 후)
```

`strategy.py`를 따로 두는 이유는 `server_app.py`가 배선만 하게 두기 위해서다. 실패 판정과
집계 정책이 앱 파일에 섞이면 테스트할 때 Flower 런타임이 필요해진다. 전략을 분리하면
`aggregate.py`처럼 **프레임워크 없이 단위 테스트가 돈다.**

### 2-1. `fl/strategy.py` — `WeldFedAvg`

```python
class RoundFailure(RuntimeError): ...

class WeldFedAvg(FedAvg):                      # flwr.serverapp.strategy.FedAvg
    def __init__(self, *, expected_nodes: int, canonical_keys, reference_sd,
                 accounting: AccountingMatrix, **kw): ...
    def configure_train(self, server_round, arrays, config, grid): ...
    def aggregate_train(self, server_round, replies): ...
    def configure_evaluate(self, *a, **kw) -> list: return []
    def aggregate_evaluate(self, *a, **kw): ...
```

**`aggregate_train`이 하는 일 (순서 고정)**

1. `replies`를 리스트로 굳히고 `msg.has_error()`로 에러를 **직접 센다.**
   에러가 1건이라도 있으면 `RoundFailure` — 재정규화 집계로 넘어가지 않는다.
2. 유효 응답 수 != `expected_nodes` → `RoundFailure`. 응답이 아예 안 온 노드는 에러 메시지도
   없으므로 **개수 검사가 유일한 탐지 수단**이다.
3. 각 응답에서 `ArrayRecord` → ndarray 리스트로 복원하고 `serialize.assert_compatible`로
   키·shape·dtype을 검사한다.
4. **집계는 `super().aggregate_train`이 아니라 `fl.aggregate.weighted_fedavg`가 한다.**
   상위 구현은 BN buffer 정책(`num_batches_tracked` 최댓값 통과)을 모르고 전부 가중 평균한다.
   정수 카운터를 평균하면 반올림이 끼어들어 어느 클라이언트의 값도 아니게 된다.
5. 회계 셀을 `AccountingMatrix`에 적재한다. 라운드별 norm·바이트·실사용 optimizer 포함.

**평가 라운드는 쓰지 않는다.** `fraction_evaluate=0.0`, `min_evaluate_nodes=0`을 하드코딩하고
`configure_evaluate`가 빈 리스트를 돌려준다. 라운드별 val 곡선은 서버가 직접 산출하며
(게이트 #6 결정 B), 클라이언트 평가 경로를 열어 두면 평가셋 접근 경로가 하나 더 생긴다.
`aggregate_evaluate`도 같은 실패 검사를 대칭으로 건다 — 열리지 않는 경로라도 열렸을 때
조용히 통과하면 안 된다.

### 2-2. `fl/server_app.py`

```python
app = ServerApp()

@app.main()
def main(grid: Grid, context: Context) -> None:
    cfg  = context.run_config          # cell, num-server-rounds, local-epochs, seed, ...
    cell = cfg["cell"]                 # "sep_fed" | "uni_fed"
    ...
    strategy = WeldFedAvg(...)
    result = strategy.start(grid=grid, initial_arrays=initial, num_rounds=R,
                            train_config=train_cfg, evaluate_fn=server_val_fn)
    audit = accounting.audit()
    accounting.to_csv(out / "accounting.csv"); accounting.to_json(out / "accounting.json")
    if not audit.ok:
        raise RoundFailure(...)        # run 무효. 채점 금지
```

- **`cell` 분기는 초기 파라미터·정본 키·클라이언트 앱 선택에만 걸린다.** 라운드 루프는 두 칸이
  같은 코드를 탄다. 칸마다 루프가 갈라지면 그 차이가 결과에 섞인다.
- `evaluate_fn`(중앙 평가 콜백)은 **val 기준**으로만 동작한다(학습 풀 10%). 글로벌 평가셋은
  전 실험 최종 채점 1회만 접근한다.
- 마일스톤 라운드(25/50/75%·최종)에서만 글로벌 파라미터를 디스크에 남기고, 최신본은
  `latest/` 슬롯에 덮어쓴다(라운드 단위 재시작 복구용).

### 2-3. `fl/client_det.py`

```python
app = ClientApp()

@app.train()
def train(msg: Message, context: Context) -> Message:
    weights_in = arrayrecord_to_ndarrays(msg.content[ARRAYS_KEY], canonical_keys)
    result = train_round(                      # 3칸 공통 진입점 — 그대로 부른다
        data_yaml=..., model=..., total_epochs=N, local_epochs=E,
        round_idx=r, client_idx=k, base_seed=s, num_examples=n_k,
        weights_in=weights_in, canonical_keys=keys, project=abs_path,
    )
    return Message(content=RecordDict({
        ARRAYS_KEY:  ndarrays_to_arrayrecord(result.ndarrays, keys),
        METRICS_KEY: MetricRecord({"num-examples": result.num_examples,
                                   "epochs-ran": result.epochs_ran,
                                   "optimizer-steps": result.optimizer_steps,
                                   "param-l2": result.param_l2_norm,
                                   "payload-bytes": result.payload_bytes,
                                   "optimizer": ..., "lr": ..., "momentum": ...}),
    }), reply_to=msg)
```

- **클라이언트는 무상태다.** 라운드마다 트레이너를 새로 만들고 상태를 액터 수명에 걸지 않는다.
- **실사용 optimizer·lr·momentum을 메트릭으로 함께 올린다.** 설정에 무엇을 적었는지가 아니라
  무엇이 돌았는지를 서버가 회계에 적어야 `optimizer='auto'` 교체가 잡힌다.
- `weighted_by_key = "num-examples"` — Message FedAvg의 가중 키 이름과 맞춘다.
- 예외는 삼키지 않는다. 실패하면 Flower가 에러 응답을 만들고 전략이 라운드를 중단시킨다.

### 2-4. `fl/client_vlm.py`

이번 과제에서는 **골격만** 만든다. RQ 우선순위 변경으로 분리형 세 칸이 논문 본체가 됐고,
통합형 학습 본체는 그 완주 뒤로 미뤄졌다. 다만 교환 단위가 다르다는 점(전체 state_dict가
아니라 LoRA 어댑터만)이 인터페이스에 드러나야 하므로, 어댑터 키 집합을 인자로 받는 형태로
자리를 잡아 둔다. 30번 명세의 G2(교환 폐포 감사)가 통과해야 본체를 채운다.

## 3. 아래층과의 호출 관계

```
                    ┌─────────────────── fl/server_app.py ───────────────────┐
                    │  @app.main()  →  WeldFedAvg.start(grid, ...)           │
                    └───────┬──────────────────────────────┬─────────────────┘
                            │ configure_train              │ aggregate_train
                            ▼                              ▼
                     ArrayRecord 배포            fl/strategy.py WeldFedAvg
                            │                              │
                            │                    ①실패 직접 검사 (has_error + 개수)
                            │                    ②serialize.assert_compatible
                            │                    ③fl/aggregate.weighted_fedavg
                            │                    ④detection/budget_audit 적재
                            ▼
              ┌──── fl/client_det.py @app.train() ────┐
              │  detection/round_runner.train_round   │──▶ detection/fed_trainer
              │    (3칸 공통 진입점)                   │      (Ultralytics 래퍼)
              │  detection/serialize (복원·직렬화)     │
              └───────────────────────────────────────┘
```

| 아래층 | 이 계층이 부르는 지점 | 왜 그대로 두는가 |
|---|---|---|
| `round_runner.train_round` | `client_det.train()`에서 1회 | 로컬·중앙 칸이 `R=1, E=N`으로 **같은 함수**를 탄다. 클라이언트가 다른 경로를 만들면 "구조 내 동일"이 깨진다 |
| `serialize` | 클라이언트 복원·직렬화, 전략의 무결성 검사 | 키 순서·dtype이 어긋나면 조용히 오염된다. 교환 경계 양쪽에서 같은 함수를 쓴다 |
| `aggregate.weighted_fedavg` | `WeldFedAvg.aggregate_train` | BN buffer 정책이 여기 있다. 상위 구현으로 대체하면 `num_batches_tracked`가 평균된다 |
| `budget_audit.AccountingMatrix` | 라운드마다 셀 적재, 종료 시 감사 | 머지 차단 조건. 빈 셀이 곧 실패다 |

**`fed_trainer`는 이 계층이 직접 부르지 않는다.** `train_round`를 통해서만 닿는다.

## 4. WeldLLM 참고 범위

| | 판단 |
|---|---|
| **참고한 것** | **이 과제 범위에서는 없다.** |
| **배제한 것** | 학습 스크립트 구조 전체 |

솔직히 적는다. WeldLLM은 단일 기관 학습이라 **라운드 경계·가중치 교환·클라이언트 개념이
아예 없다.** FL 앱 계층은 정확히 그 세 가지로만 이루어져 있으므로, 이 과제에서 가져올 구조가
없다. 억지로 참고했다고 적는 편이 더 나쁘다.

배제 근거는 총괄이 짚은 그대로이며 전부 우리가 실측한 것이다. WeldLLM에는 `final_eval()`의
`best.pt` 로드, `EarlyStopping`, `optimizer='auto'`, EMA 저장을 막는 장치가 없다. 우리
`fed_trainer.py`가 그 넷을 접촉점 4곳으로 막아 두었는데, 학습 스크립트 구조를 옮기면
그 방어가 우회되는 경로가 생긴다.

**참고가 실제로 유효해지는 지점은 따로 있다** — 검출기 출력을 VLM 프롬프트로 넘기는
접합부 인터페이스다. 그것은 분리형 판정부·통합형 추론 경로(Phase 2 이후)의 문제이고,
그때 `vlm/coords.py`를 반드시 통과시켜 좌표계를 우리 규약으로 바꾼 뒤 참고한다. WeldLLM은
Qwen2.5-VL(리사이즈 절대 픽셀) 기준이고 우리는 Qwen3.5 4B이므로, 프롬프트·파서를 그대로
옮기면 IoU가 붕괴한다(함정 #4).

Flower 쪽은 Apache-2.0이고 이 설계가 참고한 것은 **공개 API 사용 패턴**(`@app.main()`,
`@app.train()`, `Strategy.start`)이다. 코드를 복사하지 않았으므로 파일 헤더 고지 대상이
아니다. 복사가 필요해지면 출처와 원저작권을 헤더에 남긴다.

## 5. 구현 전 실측 — **완료 (2026-08-23)**

설계 단계에서 추측으로 적지 않고 전부 찍었다. 4번만 시뮬레이션 실행이 필요해 파일럿으로 미뤘다.

### 5-1. `ArrayRecord` ↔ ndarray 왕복 — **0차원·int64 보존 확인** ✅

우리 교환 규약이 내보내는 형태(float32 다차원 + **0차원 int64** `num_batches_tracked`)를
그대로 왕복시켰다.

| 원본 | 복원 | 판정 |
|---|---|---|
| `conv.weight` (2,3) float32 | (2,3) float32, 값 일치 | OK |
| `bn.num_batches_tracked` **() int64** | **() int64**, 값 일치 | **OK** |
| `bn.running_mean` (4,) float32 | (4,) float32, 값 일치 | OK |

`np.ascontiguousarray`가 0차원을 `(1,)`로 뭉갰던 것과 달리 `ArrayRecord`는 shape·dtype을
그대로 지킨다. **교환 규약을 바꿀 필요가 없다.**

**키는 인덱스 문자열로 바뀐다**(`['0','1','2']`). 리스트 경로는 이름을 보존하지 않는다.
`from_torch_state_dict`는 이름을 보존하지만(`['conv.weight', 'bn.num_batches_tracked']`,
0차원 int64도 보존) **쓰지 않는다** — 그 경로는 모델 dtype을 그대로 실어 우리 규약(부동소수
fp32 승격, 정수 원 dtype 유지)을 우회한다. dtype 정책의 정본은 `serialize.py`다.

**채택**: `serialize.state_dict_to_ndarrays`로 규약을 적용한 리스트를 만들고 `ArrayRecord(list)`로
감싼다. **순서 보존은 실측 확인됨**(8개 텐서 왕복 일치). 이름은 정본 키 리스트가 관리하고,
서버가 `keys_digest`를 메트릭으로 받아 대조한다.

### 5-2. 직렬화 바이트 — **텐서당 정확히 128 B 상수** ✅

| 측정 | 값 |
|---|---|
| `sum(a.nbytes)` | 32 B (텐서 2개) |
| `sum(len(v.data))` | 288 B → 차 **256 B = 2 × 128** |
| `rec.count_bytes()` | 290 B (= 288 + 키 문자열 2 B) |

텐서당 128 B는 npy 헤더이며 총괄 실측(496 텐서 × 128 = 63,488 B)과 정확히 일치한다.
**정확 일치 단정을 넣지 않는다.** 통신량은 `payload_nbytes`(순수 데이터)와
`count_bytes()`(직렬화 총량) **2열로 분리 기록**한다(30번 명세 판정 15).

### 5-3. `Grid`·`Message` 시그니처 ✅

- `Grid`는 `flwr.serverapp.Grid`(= `flwr.server.Grid`). `flwr.app.Grid`는 **없다**.
  메서드: `create_message`, `get_node_ids`, `push_messages`, `pull_messages`,
  `send_and_receive`, `set_run`, `run`.
- `Message(*, dst_node_id, message_type, content, error, ttl, group_id, reply_to, metadata)`.
  응답은 `reply_to=` 또는 `msg.create_reply(content)`. 판정용 `has_content()`·`has_error()` 존재.

### 5-4. Ray 액터 GPU 메모리 해제 — **파일럿으로 이월**

시뮬레이션 실행이 필요해 이 단계에서 닫지 못했다. 검출 클라이언트를 `num_gpus=1.0` 순차로
두는 기본값은 유지하며, 라운드 간 VRAM 해제는 16GB 파일럿에서 실측한다.

### 5-5. `MetricRecord` 키 규약 ✅

하이픈 키가 허용된다(`['num-examples', 'epochs-ran']`). Message `FedAvg`의 기본
`weighted_by_key`가 **`"num-examples"`**이므로 클라이언트가 그 이름으로 표본 수를 올린다.
`arrayrecord_key` 기본 `"arrays"`, `configrecord_key` 기본 `"config"`.

### 5-6. 명세 F23의 1.34 서술이 1.33.0에서 성립하는가 — **전부 성립** ✅

| F23 서술 | 1.33.0 실측 |
|---|---|
| Message `FedAvg`에 `accept_failures` 없음 | ✅ 없음 |
| `aggregate_train`이 `_check_and_log_replies`로 에러를 버린 뒤 집계 | ✅ `fedavg.py` L188, 소스 확인 |
| 흔적은 INFO 로그 한 줄 | ✅ `log(INFO, "%s: Received %s results and %s failures", ...)` |
| **`fraction_evaluate` 기본 1.0** | ✅ **1.0** |
| 레거시에는 `accept_failures: bool = True` | ✅ L109 |

추가 실측: `min_train_nodes=2`, `min_evaluate_nodes=2`, `min_available_nodes=2`가 기본값이다.
**우리는 3클라이언트 전수 참여가 전제이므로 셋 다 3으로 명시 고정한다** — 기본 2를 두면
한 클라이언트가 빠져도 라운드가 성립한다.

명세의 버전 표기 2곳(L413·F23)을 `1.33.0`으로 정정했다.

## 6. 테스트 계획 (프레임워크 없이 도는 것을 우선한다)

| 대상 | 검사 |
|---|---|
| `WeldFedAvg.aggregate_train` | 에러 응답 1건 → `RoundFailure` / 응답 수 부족 → `RoundFailure` / 정상 3건 → 집계 성공 + 회계 셀 3개 |
| 〃 | **재정규화가 일어나지 않음** — 2/3만 응답한 상태로 집계가 성공하면 실패로 판정 |
| `configure_evaluate` | 항상 빈 리스트 |
| 회계 연동 | 라운드 R 완주 후 `audit().ok`, 중간 이탈 시 빈 셀 검출 |
| ArrayRecord 왕복 | 0차원·int64 보존 (실측 항목 1 확정 후) |

`WeldFedAvg`는 `flwr.serverapp.strategy.FedAvg`를 상속하므로 flwr import가 필요하다.
따라서 테스트 파일 상단에 `pytest.importorskip("flwr")`를 건다 — 기본 스위트가 선택적
의존성 없이 완주해야 한다는 원칙(게이트 반려 이력)을 따른다.
