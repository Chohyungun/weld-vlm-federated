  5. §3-4 — "역변환은 어댑터 안에서 정확히 1회"(C안: 역변환은 C의 추론 스크립트에서 1회,

  6. §9 `check-coords` — 왕복 테스트의 대상 모듈 경로
  7. §10 좌표 변환 테스트 행 — 동일

  `coord_cfg_hash` + `resized_wh` + `transformers_version`을, D는 `coord_space`(original_px/…)
  + `coords_spec_version`을 쓴다 — **같은 개념에 어휘 두 벌**이다. 계약 #4 확정본은 한 벌만
  남겨야 한다(게이트 문구는 C 어휘 기준: `bbox_px` + `convention`·`coord_cfg_hash`).
- **실패 시나리오**: 스키마만 고치고 §3-4를 남기면, D 구현자가 어댑터에 역변환을 넣는다 →
  C가 이미 역변환한 `bbox_px`에 이중 역변환 — D 자신의 실패 경로 표 #10("이중 역변환")이
  경고한 바로 그 사고가 트랙 경계에서 재발한다.
- **근거**: 게이트 기록 §5-1 판정·"C는 규약 소유자, D는 검증 소유자" / 리뷰 배분에서 D에 지정된 점검 범위
- **제안**: 위 7곳을 한 커밋으로 일괄 개정하고, D의 검증 자산(Q20 실측·D1 정밀화·오라클
  카나리·시각 카나리·발행 게이트)은 게이트가 명시했듯 **전부 존치한다** — 이것들은 소유권과

### [Important] 13_spec_D:§8-3 — "라운드 r 글로벌 모델을 글로벌 평가셋으로 채점해 step=r 로깅"이 C의 확정(학습 중 평가 전면 제거)과 트랙 간 정면 충돌

- **요약**: D §8-3은 구현설계 7-4를 그대로 계승해 서버 evaluate 콜백의 라운드별 평가셋
  채점을 명세했다. C는 함정 #1에서 같은 문구를 "평가 자산 격리 원칙과 충돌"로 명시 기각하고
  **학습 중 글로벌 평가셋 접근 0회 + 완주 후 보존 체크포인트 사후 채점**으로 확정, 구현설계
  7-4 문구 정정을 게이트 안건으로 올렸다. 두 스펙이 같은 정본의 서로 다른 개정안을 전제한다.
- **실패 시나리오**: D가 §8-3대로 라운드별 지표 CSV(`round, loss, macro_f1, …`)를 요구하는
  `log_run.py`를 구현(누락 즉시 실패 정책!) → C의 서버는 loss·norm만 보냄 → 러너가 매
  라운드 실패하거나, 메우려고 D가 라운드마다 평가셋 채점을 자체 실행 → C가 지키려던 "접근
  0회" 주장이 D의 배관에서 깨진다.
- **근거**: 12_spec_C §2-2·Q3, 12a 함정#1 L90 / docs/개발규약.md 데이터 규칙 4 / 트랙 C 리뷰
  (20_review_적대_C.md Important #1 — 같은 사안의 C 내부 모순)
- **제안**: 총괄이 구현설계 7-4 정정 안건을 닫을 때 **C·D를 동시 개정한다.** D 쪽 최소 수정:
  §8-3을 "라운드 중 실측 로깅 = loss·norm·바이트(C 제공)"와 "라운드별 지표 곡선 = 완주 후
  보존 체크포인트를 D 채점기로 사후 산출해 같은 run에 backfill(step=r)" 2단으로 재정의.
  라운드별 CSV의 지표 열은 사후 채움 열로 명시.

### [Important] 13_spec_D:§4-3 — 다결함 이미지의 판정 정합성 재계산 규칙이 미정의

- **요약**: 재계산 절차가 "예측 결함의 size_mm"라고 단수로 서술돼 있다. 이미지에 결함이
  여러 개이고 인용 조항이 여러 개일 때 어느 결함·어느 조항 짝으로 부등식을 세우는지,
  이미지 합부는 결함별 판정을 어떻게 합성하는지(전부 합격=합격? 최악 기준?)가 없다.
- **실패 시나리오**: 기공 2mm + 균열 4mm 이미지, cited_clauses[0]이 기공 조항 → 구현 A는
  기공 size로 재계산(합격), 구현 B는 최대 결함 size로 재계산(불합격) → 같은 레코드가
  구현에 따라 정합/부정합이 갈린다. 단일 채점기라도 **규칙이 미정의면 재현 불가와 같다.**
  더 나쁘게, B의 골격 생성기가 gold verdict를 만들 때 다른 합성 규칙을 쓰면 지표가 계통
  편향된다.
- **근거**: 실험설계 8-3(판정 정합성 정의) / docs/개발규약.md 데이터 규칙 7(허용치 단일 소스 —
  규칙도 단일이어야 정합)
- **제안**: "결함 인스턴스별로 (해당 결함코드에 대응하는 인용 조항, size) 짝을 재계산 →
  **하나라도 불합격이면 이미지 불합격**(보수 규칙, 검사 실무 관례)"으로 명시하고, 이 합성
  규칙을 **B의 골격 생성기와 같은 함수 또는 같은 명세로 공유한다**(계약 #3에 부속 규칙으로
  편입 제안). 단위 테스트에 다결함 케이스 3종(전합격/혼합/전불합격)을 추가.

### [Important] 13_spec_D:§1 검사 2 — 누출 해시 검사가 전제하는 `consumed_image_ids.txt`가 C의 어떤 산출물 목록에도 없다

- **요약**: "학습 러너가 남긴 consumed_image_ids.txt를 대조한다"는 격리 방어선의 절반이
  C의 협조 산출물인데, C 스펙(12_spec·12a)의 RoundResult·감사 산출물 어디에도 이 파일이
  없다. C의 V11(data.yaml 전수 grep)은 검출 칸의 유사 장치지만 파일 단위가 다르고 VLM
  칸(D4 페어 로더)은 커버가 불명확하다.
- **실패 시나리오**: 구현 단계에서 C는 V11로 충분하다고 보고 consumed_image_ids를 만들지
  않는다 → D의 검사 2가 영구 skip 또는 형식적 통과 → 논문 철회 사유급 방어선이 실제로는
  작동한 적이 없는 채로 "격리 검증 완료"를 주장하게 된다 — 검증 미도달을 통과처럼 쓰는
  것(루브릭 과잉 주장 #4)의 파이프라인 판이다.
- **근거**: docs/개발규약.md 데이터 규칙 4 / 12a V11 / 13_spec_D §1
- **제안**: consumed_image_ids(칸·시드별, 검출은 data.yaml 전개 결과, VLM은 로더 소비 로그)
  를 **C→D 산출물 계약에 정식 등재**하거나, D 검사 2를 "C의 V11 산출물 + D4 로더 필터
  assert 로그"를 입력으로 재정의한다. 어느 쪽이든 계약 없는 전제를 없애는 것이 목적이다.

### [Important] 13_spec_D:§4-11·Q7 — 가정값 3종(px_per_mm·thickness·quality_level)이 B의 생성 경로와 단일 소스로 묶여 있지 않다
