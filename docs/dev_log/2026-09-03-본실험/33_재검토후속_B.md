## 3. `missing_contract` — 명부 판정과 목록 단일화

`5c74461` 이 `frozen_out.EXPECTED_SEALED` 명부(7곳: expected 3 · lost 4, `owner`·`record` 포함)와
판정 넷(`missing_contract` 실패 · `absent_tree` 알림 · `lost_recorded` 알림 · `lost_but_present` 실패),

**이번에 더한 것 — 목록 단일화.** 지시는 `verify_backup.DEFAULT_DIRS` 를 명부로 재사용하라고
했다. 방향을 반대로 했다: **명부(`frozen_out`)가 정본이고 `verify_backup.DEFAULT_DIRS` 가 거기서
파생된다.** 이유는 층위다 — `verify_backup` 이 `frozen_out` 을 import 하므로 반대로 두면 순환
import 다. 결과는 같다. 목록이 하나다.

```python
SEALED_DIRS   = 명부에서 status == "expected" 인 것   # cycle_pilot · cycle_pilot_v2 · pairs_pilot_v1
UNSEALED_DIRS = (corpus/validate/judge_labels,)      # 과제 4
DEFAULT_DIRS  = SEALED_DIRS + UNSEALED_DIRS
```

소실 기록(v2·pilot3000 셋)은 옮길 실물이 없으니 목록에서 빠지고, `plan` 이 "소실 기록 4곳은 …
명부 대조기가 알린다" 를 찍는다. 회귀 시험 `test_백업_목록은_봉인처_명부에서_파생된다` 가 두 목록의

같은 트리에서 명부를 비우면 exit 0 에 `pairs_pilot_v2` 라는 글자가 안 나온다 — 09-11 의 출력이다.

## 4. `judge_labels/` 백업 편입 + 라벨 추적/가명화 제안

`build_plan` 이 계약서 없는 디렉터리를 거부하던 것을, **명시된 `UNSEALED_DIRS` 에 한해** 있는 파일
전부를 담도록 바꿨다(아무 디렉터리나 넘기면 여전히 "봉인본이 아니다"). 항목에 `sealed: False` 를
남겨 `verify` 가 계약서 대조가 없다는 것을 안다. 실물 `plan`:

```
  ㆍ○ judge_labels/sheet_v1.jsonl        16,694 B   (추적)
  ㆍ○ judge_labels/sheet_v1.meta.json       954 B   (추적)
  ★○ judge_labels/sheet_v1.strata.json    1,776 B   (git 밖 — 유일본)
파일 23개 / 3.29 MB · ★ 15개
```

`labels_*.jsonl` 은 아직 없다. 생기면 같은 자리에서 ★ 로 잡힌다 — 시험
`test_사람_라벨_폴더가_백업_목록에_있고_미추적분이_위험분으로_잡힌다` 가 그 경로를 픽스처로 고정한다.

**제안 — 라벨은 미추적 유지, 처음부터 가명 필드로, 드라이브 백업.** 판정은 총괄.

- **추적하지 않는다.** `labeler` 는 사람 이름이고 `note` 는 자유 기술이다 — 규약 2-6 의 개인 정보다.
  공개 저장소에 올릴 것이 아니다.
- **가명화는 나중이 아니라 시트 단계에서.** `labeler` 를 `L1`·`L2` 같은 코드로 적게 하고, 실명↔코드
  대응은 미추적 파일에 둔다. 그러면 나중에 추적 전환을 판정하더라도 파일을 고칠 일이 없다.
- **추적 전환은 권하지 않는다.** 추적 중인 `EVIDENCE.jsonl` 이 항목별 기계 판정을 이미 들고
  있으므로, 라벨까지 추적하면 항목별 "사람 대 기계" 가 공개된다. 과학적으로는 문제없지만 라벨러
  코드와 자유 기술이 함께 나가고, 표본 25건의 소규모라 코드만으로도 추정될 수 있다. 백업은 드라이브로
  충분하다.
- 위 두 가지(코드 필드·대응표 위치)는 `judge_labels sheet` 의 안내문에 넣을 수 있다. 판정 후 한다.
