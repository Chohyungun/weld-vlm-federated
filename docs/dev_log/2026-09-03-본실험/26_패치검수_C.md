### 2-2. F02 — mosaic 종료 중복 → 사실 확인(원인 판정 없음)

- 우리 쪽: `detection/fed_trainer.py:263-265` `_setup_train` (e) — `start_epoch >= epochs − close_mosaic` 이면 `_close_dataloader_mosaic()` + `train_loader.reset()`.
- 상류: `ultralytics/engine/trainer.py:454-456` 루프 — `epoch == epochs − close_mosaic` 에서 같은 두 호출. 상류 `resume_training`(1082-1084)의 `start_epoch > …` 분기는 `args.resume` 경로라 우리 경로에서는 돌지 않는다.
- 횟수(E=2·N=100·close_mosaic=10 → 경계 90): **`start_epoch == 90` 인 연합 라운드 45 만 두 번**(setup 1 + 루프 1). 92 이상 라운드는 setup 1 번(루프 조건 거짓). 중앙·로컬은 루프 1 번. 감사자 문장과 일치.
- 사실 추가: `InfiniteDataLoader.reset()` 은 이터레이터를 새로 만들고(`ultralytics/data/build.py:101-104`), torch 는 이터레이터 생성 시 `loader.generator` 에서 `_base_seed` 를 뽑는다(`torch/utils/data/dataloader.py:706-708`) → 여분의 reset 은 생성기 상태를 한 번 더 소비한다. 기본 정책에서는 연합이 라운드마다 새 생성기라 어차피 중앙과 순열이 다르고(F01), opt-in 정책에서는 매 epoch 재시드 뒤 reset 이 오므로 라운드 45 와 중앙 모두 "재시드 → reset(재시드) → reset(루프)" 로 소비 횟수가 같다. **패치는 이 동작을 바꾸지 않았다**(handoff: "종료 동작 자체는 바꾸지 않았다"). 원인 확정은 하지 않는다.

### 2-5. F05 — 재개 궤적·회계 → 수용 + 수정 제안 1 + R 연계 1

- **누적 갱신·LR 이력.** 체크포인트 payload 에 `optimizer_updates`·`lr_trace`(`resume.py:235-237`), 재개 시 `trainer.n_optimizer_updates` 복원(`round_runner.py:325`)·`_LRTrace(previous)` 이어 붙임. Codex 시험 `test_resume_preserves_update_total_and_full_lr_trace_across_two_processes` 가 47 스텝·16 갱신·2 항목 LR 이력을 고정한다. **범위 정정(외부 지적 수용)**: 이름의 `across_two_processes` 와 달리 이 시험은 한 프로세스 안에서 `_FakeTrainer` 두 개를 만들어 저장→로드→재저장을 도는 **직렬화 왕복 시험**이다. 프로세스 경계(파이썬 재기동·RNG 재초기화·CUDA 컨텍스트)는 건너뛴다. 초안이 이를 '두 프로세스에 걸친' 으로 쓴 것은 과대 서술이었다 — 이 시험이 사는 것은 **payload 왕복의 회계 보존**이고, 실제 프로세스 경계 재개는 여전히 미검증이다(§4-2 조건 5).
- **좌표 환산·거부.** `validate_detection_resume`(`round_runner.py:398-421`): `0 < consumed <= E`, `next_epoch == r·E + consumed`(`next_epoch = epoch_done + 1`, `resume.py:117-120`), 완료 체크포인트 거부, 구판 필드 결측 거부, 갱신 횟수 범위, LR 이력 완비. 호출은 `resume_dir` 이 있고 상태가 있을 때만(`round_runner.py:312`). `_setup_train` 에도 같은 완료 가드(`fed_trainer.py:211`). 회계 `ran_here` 는 `epochs_this_process` 우선, 없으면 `resumed_from_epoch − r·E` 환산(`budget_audit.py:277-285`).
- **독립 재현(`repro_f05.py`).** (1) 라운드 2 를 전역 epoch 5 에서 재개·stopper 0 회 셀: 패치 전 감사 **통과(결함 — `ran_here = 2 − 5 < 0`)**, 패치 후 실패("stopper 호출 0회 < 이 프로세스가 돈 epoch 1회"). (2) `RoundBudget(E=2, resumed=2)` 는 첫 epoch 종료 콜백 뒤에야 `stop` → 패치 전 추가 1 epoch 가능(재현), 패치 후 `validate_detection_resume` 가 "라운드 예산이 이미 완료된 체크포인트" 로 거부.
- **경계 일치.** handoff "완료 체크포인트의 자동 최종 export·누적 gradient 동치는 미완" ↔ 코드는 완료 체크포인트를 **거부만** 하고 export 를 만들지 않으며 gradient 잔여는 저장하지 않는다. 일치.
- **수정 제안.** 거부 메시지 "이 파일을 보존하고 최종 가중치 내보내기 상태를 확인하라" 는 ②③(단일 run, 100 epoch 완료 뒤 저장 전 사망)에만 맞는다. **④ 에서 클라이언트가 E epoch 를 다 돌고 서버에 보내기 전에 죽으면 서버는 그 갱신을 받은 적이 없다** — 처치는 "내보내기" 가 아니라 **라운드 경계에서 다시 돌리기**다. 메시지에 칸별 처치를 나눠 적기를 권한다(한 줄).
- **R 연계.** 위 ④ 처치가 정확히 wt/C-bdr 의 R(닫힌 접두 k 로 되돌아가 k+1 부터, `_resume` 잔해 격리)이다. 패치의 거부와 R 의 재개는 상보적이다(§4).

## 8. 외부 검토자 5건에 대한 답 (codex_reply.md "### C — 다음 재개 실험 전에 확인할 것")

### 8-1. 이전 loss CSV 삭제 경로 → **수용(결함 확인), 시험 미작성**
`ultralytics/engine/trainer.py:199-201`: `if self.csv.exists() and not self.args.resume: self.csv.unlink()`.
우리 재개는 상류 `args.resume=False` 로 도는 커스텀 경로이므로, 같은 `save_dir` 로 트레이너를 다시 만들면 **이전 `results.csv` 가 지워진다.**
패치가 복원하는 것은 `lr_trace`(LR 이력)뿐이고 과거 loss 행은 복원하지 않는다 — 검토자 지적대로다.
영향 범위: ④ 는 라운드마다 `runs/r{r}_c{c}` 로 경로가 갈려 라운드 간에는 무관하고, **같은 라운드를 epoch 재개할 때만** 그 라운드의 앞 epoch 행이 사라진다.
세 시드 본실험은 재개 0 이라 실제 손실은 없다(§2-5 감사 결론과 같다). 조치 제안: 재개 시 기존 CSV 를 `results.before_resume_{stamp}.csv` 로
보존하고 새 파일에 이어 쓰되, epoch 중복 행은 뒤엣것을 채택. 시험은 "재개 후 CSV 에 이전 epoch 행이 남아 있고 중복이 없다" 로.
**이번 검수에서는 시험을 만들지 않았다** — 패치 범위 밖이고 R 착지·후속 프로토콜과 함께 설계해야 한다.

### 8-2. 복구 파일 정리 시점 → **수용(순서 결함 확인)**
`round_runner.py:361-363` 이 `train_round` 반환 **전에** `clear_resume(resume_dir)` 를 부르고, 최종 NPZ 는 그 뒤 호출자
(`train_cell.py:117·171` `save_cell_weights`)가 저장한다. 그 사이(메모리에만 있는 구간)에 프로세스가 죽으면 **복구 파일도 없고 최종 NPZ 도 없다.**
올바른 순서는 "내구 저장 → 검증(재로드·해시) → 정리" 다. 조치 제안: `clear_resume_on_success` 를 기본 False 로 두고 저장·검증을 마친
호출자가 명시적으로 정리하거나, `train_round` 가 저장 콜백을 받아 저장 성공 후에만 정리. 검증 시험은 저장 함수에 예외를 주입해
복구 파일이 **남는지** 확인하는 형태(검토자 제안 그대로). 이것도 패치 범위 밖이라 이번에 만들지 않았다.

### 8-3. AMP 갱신 카운터 의미 → **수용(의미 정정), 현 산출물 영향 없음**
`fed_trainer.optimizer_step`(314-331)은 상류 `optimizer_step` 을 부른 뒤 `n_optimizer_updates += 1` 한다.
상류는 `scaler.step(self.optimizer)`(`trainer.py:846`)를 쓰고, `torch.amp.GradScaler.step` 은 비유한 gradient 를 만나면
`optimizer.step()` 을 **건너뛴다**(inf/NaN 발견 시 skip). 따라서 현재 값은 "갱신 성공 횟수" 가 아니라 **"갱신 시도 횟수"** 다.
정정 방법 두 가지: (a) 이름·문서를 `optimizer_step_attempts` 로 바꿔 의미를 맞추거나, (b) `scaler.get_scale()` 변화 또는
`_check_inf_per_device` 로 skip 을 세어 성공 수를 따로 남긴다. **기존 세 시드에 실제 skip 이 있었다고 단정하지 않는다** — 검토자와 같은 입장이고,
현 원장은 v2 라 `amp` 실효값 지표가 없어 사후 확인도 불가능하다(G14 의 `amp` 는 R 착지 후 v3 부터). ②③ meta.json 의 `amp` 는 세 시드 모두 `null`.
논문·보고에서 이 수를 "총 갱신 횟수" 로 인용할 때 각주가 필요하다.

### 8-4. 새 정책과 기존 출력 경로 충돌 거부 → **수용, 제안 강화**

그대로 있고, 채점 경로는 이미 쓰는 것을 재사용한다 — `evaluation/detect_infer.load_yolo_from_npz` 로 npz 를 올리고 `scripts/main_det.py export`
와 **같은 추론 설정**(fp32·CPU·imgsz 640·conf 0.01·max_det 300·`ABS_ORIG`)으로 돌린 뒤 단일 채점기에 넣으면 된다. 비용은 시드 1 벌당 12,461 장에
56 분이었으므로 5,001 장 × 4 시점 × 3 시드 = 12 회가 대략 **4~5 시간 CPU**(GPU 를 쓰면 훨씬 짧지만 채점 경로는 CPU 고정이 규약이다).
필요한 준비는 셋뿐이다. ① 고정 표본을 쓸지 5,001 장 전체를 쓸지 **회의에서 확정**(표본이면 층화 기준과 난수 시드를 먼저 고정해야 사후 선택이 되지 않는다).
② 산출물을 기존 `predictions/` 와 섞지 않도록 별도 경로(`outputs/diag_c/mosaic_transition/`)와 `DO_NOT_CITE` 표식.
③ 해석 한계를 미리 문서에 박아 둘 것 — 이 대조는 "학습 손실만 변했는지, 고정 입력의 검출 성능도 변했는지" 를 보여줄 뿐
**원인(loader 난수 vs mosaic 전환)을 분리하지 못한다.** 회의 문서도 같은 단서를 달았고, 라운드당 2 epoch 이라 91 epoch 모델은 존재하지 않는다는 점도 그대로다.
**회의 확정 전이므로 실행하지 않았다.**
