## 3. `restored` 어휘 — 그리고 I-1

A 가 새로 정의한 상태다: "소실 뒤 **동일 바이트**로 복원, 검사는 `expected` 와 같음, `evidence`
필수, 실물이 돌아온 뒤에만."

**대조기 쪽은 이미 맞다.** `verify_contract` 는 `status == "lost"` 만 특별히 다루고(계약서 없으면
`lost_recorded`, 있으면 `lost_but_present`) 나머지는 전부 expected 경로를 탄다 — `restored` 를
붙이면 "있어야 하고 없으면 실패" 가 된다. A 가 B 몫으로 넘긴 "명시 분기" 는 동작 변경이 아니라
어휘를 코드에 적는 일이다.

**백업 목록 쪽은 아니었다 — I-1.**

```python
SEALED_DIRS = tuple(REPO / rel for rel, e in EXPECTED_SEALED.items()
                    if e.get("status") == "expected")      # ← restored 가 빠진다
```

A 가 pilot3000 세 자리를 `restored` 로 올리는 순간, 그 세 곳은 `verify_backup` 의 목록에서
**조용히 사라진다.** 실물은 `data/processed`(정션) 한 벌뿐이고 git 밖이라, 백업 목록에서 빠진
자산은 09-11 과 같은 단일 사본 구조가 된다. 방향만 반대일 뿐 이 모듈 독스트링이 경고한
"두 목록이 따로 살면 한쪽만 고쳐진다" 그 자체다 — 기존 시험
`test_백업_목록은_봉인처_명부에서_파생된다` 도 같은 `== "expected"` 를 복창해 못 잡는다.

**A 의 잘못이 아니다**(어휘를 늘린 쪽은 규칙을 적었고, 목록을 파생하는 코드는 B 파일이다).
지금 `restored` 인 항목이 없어 실제 손실은 아직 없다. **이 커밋에서 고쳤다** —
`BACKED_UP_STATUSES = {"expected", "restored"}` 와 명부·뿌리를 인자로 받는 `sealed_dirs()` 를 두고,
픽스처 명부로 `restored` 가 목록에 드는지 고정하는 시험을 더했다. A 의 `restored` 커밋이
들어오기 전에 머지되면 창이 닫힌다.

## 9. 하지 않은 것

- `wt_A` 파일 수정·체크아웃·정션·삭제 없음. 변이는 임시 clone 에서만, 매번 원복했다(clone `git status` 0줄).

  실패했다. 본체에는 그 객체가 **있다**(`git cat-file -e` 통과) — 저장소 손상이 아니다. 게이트가 끝난 뒤
  다시 clone 해 `fsck --connectivity-only` 로 확인하고(잔여는 dangling 뿐) 그 사본에서 §5 를 다시 돌렸다.

- heavy 시험 미실행. 본체 게이트가 도는 동안에는 pytest 를 띄우지 않았다.
- A 파일 수정 없음 — I-1 은 B 파일(`corpus/validate/verify_backup.py`)에서 고쳤다.
