# 용접 결함 판정 연구 · 구현 설계 보고서

작성 2026-08-14 · 실험 총괄 보고서(v2)의 구현 편 · 소요 시간은 배제하고 구현 방안만 다룬다

이 문서는 실험 총괄 보고서가 정한 설계(다섯 칸, 세 학습 방식, 두 구조)를 코드로 옮길 때 필요한 결정을 모두 적는다. 각 절은 채택안, 대안과 근거, 선행 사례 순으로 구성했다. 항목별 정리표는 별도 엑셀(구현설계_실무정리_260814.xlsx)에 있다.

# 1. 전체 구성

## 1-1. 언어·환경

| 항목 | 채택 | 비고 |
|---|---|---|
| 언어 | Python 3.11 | 전 구간 단일 언어 |
| 프레임워크 | PyTorch 2.x + CUDA 12.x | 검출·VLM·LLM 공통 |
| 패키지 관리 | uv 또는 conda + requirements.txt 버전 고정 | pip freeze 결과를 저장소에 커밋 |
| 설정 관리 | YAML 단일 파일 + OmegaConf | 칸별 설정은 base.yaml 상속 + 차이만 override |
| 시드 | random, numpy, torch, cuda 모두 고정. cudnn.deterministic=True | 시드 값은 설정 파일에 기록 |

설정 관리에 Hydra를 쓰는 것이 요즘 연구 코드의 일반형이지만, 실험이 다섯 칸으로 고정되어 있고 스윕이 없으므로 OmegaConf 수준이면 충분하다. 도구를 늘릴 이유가 없다.

## 1-2. 저장소 구조

한 저장소(monorepo)로 간다. 파트 간 인터페이스가 파일(매니페스트, jsonl, 체크포인트)이므로 저장소를 나누면 버전 맞추는 비용만 생긴다.

```
weld-fl/
├── configs/            # base.yaml + 칸별 override 5개
├── data/
│   ├── ingest/         # AI허브 압축 해제·JSON 파싱
│   ├── convert/        # 폴리곤→bbox, COCO/YOLO 변환
│   ├── dedup/          # pHash 중복 묶음
│   └── split/          # 평가셋 선분리, 클라이언트 분할 → manifest.csv
├── corpus/
│   ├── parse/          # Docling 파싱, 표→CSV
│   ├── rules/          # 허용치 표, 판정 골격 생성기
│   ├── generate/       # vLLM 호출, QA·추론·페어 생성
│   └── validate/       # 3단계 검증, 스냅샷 해시
├── detection/          # 분리형 검출 학습 (세 칸)
├── vlm/                # 통합형 학습 (두 칸)
├── fl/                 # Flower ServerApp/ClientApp, 집계
├── rag/                # 색인 구축, 검색, 판정부 파이프라인
├── evaluation/         # 공통 채점기, 지표 산출
└── tracking/           # MLflow 설정, 체크포인트 규칙
```

## 1-3. 단일 진실 소스 원칙

모든 학습·평가 코드는 원본 폴더를 직접 읽지 않고 매니페스트를 읽는다.

- `manifest.csv`: 이미지 경로, sha256, 원본 라벨, ISO 코드, split(train/val/eval), client(C1/C2/C3), 중복 묶음 ID
- 텍스트 자산은 jsonl + 스냅샷 해시 파일(`SNAPSHOT.sha256`)
- 매니페스트가 바뀌면 실험 결과가 바뀐 것이다. 분할 확정 후에는 읽기 전용으로 잠근다

# 2. 이미지 파이프라인 (D1)

## 2-1. AI허브 데이터 해제·파싱

AI허브 라벨은 이미지당 JSON이고 결함 영역이 폴리곤 좌표로 들어 있다. 파싱 단계에서 할 일:

1. JSON 스키마를 pydantic 모델로 정의해 필드 누락·좌표 이상(음수, 이미지 밖)을 걸러낸다. 걸러진 건수를 로그로 남긴다
2. 메타데이터(type=VT/RT, material=ST/AL)를 매니페스트 컬럼으로 승격한다
3. 1주차 확인 사항인 두께·픽셀-mm 스케일 필드의 존재 여부를 이 단계에서 프로그램으로 전수 확인한다 (설명서만 믿지 않는다)

## 2-2. 폴리곤 → bbox·크기 산출

| 산출물 | 방법 | 라이브러리 |
|---|---|---|
| bbox | 폴리곤 x·y의 min/max | numpy |
| 결함 장축 길이 | 최소 외접 사각형의 긴 변 | cv2.minAreaRect |
| 등가 직경 | 폴리곤 면적에서 √(4A/π) | shapely 또는 cv2.contourArea |

- bbox와 크기는 픽셀 단위로 매니페스트에 저장하고, mm 환산은 스케일 확인 결과에 따라 별도 컬럼으로 추가한다 (원본 값을 덮어쓰지 않는다)
- 크기 값은 판정 골격 생성기(4-3)와 판정 gold의 입력이 된다

## 2-3. 중복 제거

같은 용접부 연속 촬영이 학습·평가에 갈라져 들어가는 누수를 막는 단계다.

- imagehash 라이브러리의 pHash, 해밍 거리 임계 8 이내를 같은 묶음으로 판정
- 묶음은 union-find로 연결하고 묶음 ID를 매니페스트에 기록
- 분할은 이미지 단위가 아니라 묶음 단위로 한다 (sklearn StratifiedGroupKFold의 group 인자에 묶음 ID를 넣는 방식)
- 임계값 8은 관례값이므로, 표본 100쌍을 눈으로 확인해 과병합·과분리 여부를 점검하고 값을 확정한다

## 2-4. 라벨 통일

- 사상표(원본 라벨 ↔ ISO 6520-1 코드)는 YAML 한 파일로 두고 모든 코드가 이 파일을 import한다. 코드 안에 라벨 문자열을 하드코딩하지 않는다
- 학습 라벨은 원본 5클래스(정상 포함 여부는 검출 프레임 관례에 따름: 검출에서 정상 이미지는 "박스 없음"으로 표현)
- 중간 포맷은 COCO JSON으로 통일하고, YOLO txt는 COCO에서 스크립트로 변환한다. COCO를 기준으로 두면 pycocotools 채점(8장)과 바로 연결된다
- RIAWELC 낯선 데이터 평가용 사상(공통 3클래스)도 같은 YAML에 별도 섹션으로 둔다

## 2-5. 전처리·증강

- 입력 해상도 640, letterbox 리사이즈 (Ultralytics 기본과 동일)
- 증강은 검출 프레임 기본값(mosaic, HSV, flip)을 세 칸에 동일 적용하되 설정 파일로 고정해 명시한다
- 통합형(VLM)은 증강 없이 리사이즈만 한다. 검출과 VLM은 입력 구조가 달라 전처리를 완전히 같게 만들 수 없으므로, "구조 내 동일" 원칙(분리형 세 칸끼리 동일, 통합형 두 칸끼리 동일)을 논문에 명시한다
- 방사선 이미지 특성상 색 증강(HSV)은 의미가 없거나 해로울 수 있다. 파일럿에서 mosaic+flip만 켠 설정과 비교해 하나로 확정한다

## 2-6. 분할 구현

```
절차 (순서 고정)
 1) 중복 묶음 생성 (2-3)
 2) 글로벌 평가셋 20% 선분리: 재질×클래스 층화, 묶음 단위
 3) 남은 80%를 C1/C2/C3로 분할
    - C3 = RT 알루미늄 전체 (자연 분할)
    - C1:C2 = RT 강재를 2:1로 나누되 Dirichlet(α=0.5)로 클래스 편중 부여
 4) manifest.csv 확정, sha256 기록, 읽기 전용 전환
 5) 클래스×클라이언트 분포 히트맵 생성 → 논문 그림
```

Dirichlet 분할은 클래스별로 α=0.5의 Dirichlet 분포에서 클라이언트 비율을 뽑아 배정하는 표준 방식(Hsu et al. 2019에서 제안된 이후 연합학습 non-IID 실험의 관례)을 그대로 구현한다. 함수 하나(입력: 라벨 배열, 클라이언트 수, α, 시드 / 출력: 인덱스 리스트)로 짜고 단위 테스트를 붙인다. flwr-datasets 패키지에 DirichletPartitioner가 있으나 우리는 묶음 단위 제약과 자연 분할(C3)이 섞여 있어 자체 구현이 더 단순하다.

non-IID의 관리는 별도 시스템이 아니라 매니페스트로 한다. 분할 결과가 CSV로 남아 있으므로 어떤 실험이든 같은 분할을 재사용하고, 분포 통계(클라이언트별 클래스 수)는 CSV에서 재계산 가능하다.

# 3. 검출 모델 구현 (분리형 세 칸)

## 3-1. 프레임 선택

| 후보 | 라이선스 | 판단 |
|---|---|---|
| Ultralytics YOLOv8n/s | AGPL-3.0 | 채택. 학습·검증·추론이 한 API로 묶여 구현 비용이 가장 낮다 |
| RT-DETR | Apache-2.0 | 대안 1순위. 트랜스포머 검출기, NMS 불필요. 최근 상승세 |
| YOLOX / MMDetection | Apache-2.0 | 대안. MMDetection은 유연하나 설정 비용이 크다 |

주의할 점이 하나 있다. Ultralytics는 AGPL-3.0이라 논문·연구에는 문제가 없지만, 이후 사업화 단계에서 코드 공개 의무가 붙는다. 플랫폼 제품화까지 간다면 그 시점에 RT-DETR 계열이나 상용 라이선스 구매로 갈아타는 것을 전제하고, 지금은 구현 속도를 택한다. 이 판단을 기록으로 남겨둔다.

선행 사례: AI허브 71761의 참조 모델이 YOLOv5x-seg이므로 같은 계열의 소형 모델을 쓰면 "참조 모델 대비 1/30 크기에서 어느 수준인가"라는 서사가 자연스럽다. 용접 결함 검출 문헌 다수가 YOLO 계열 개조(attention 추가, 소형 결함 대응)를 다루며, 우리는 검출기 자체를 개조하지 않고 표준 모델을 쓰는 쪽이 통제 실험 목적에 맞는다.

## 3-2. 학습 설정

- 100 epoch, batch 32, SGD(momentum 0.937), AMP, cosine LR (선행 설정 계승, 총괄 보고서 6-3)
- **조기 종료 없음.** Ultralytics 기본 patience=100이 조기 종료로 작동하므로 patience를 epoch 수 이상으로 설정해 끈다. 다섯 칸 고정 예산 원칙 때문이며, 설정 파일에 주석으로 이유를 남긴다
- best.pt가 아니라 last.pt를 채점 대상으로 한다. best 선택은 val 성능 기준의 암묵적 조기 종료와 같아서 칸 간 공정성을 해친다. last로 통일하고 val 곡선은 참고로만 로깅한다
- 로컬 칸(분리·로컬)은 같은 설정으로 C1/C2/C3 각 1회, 총 3모델

## 3-3. 연합학습에서의 검출 모델

- 교환 단위: model.state_dict() 전체를 ndarray 리스트로 직렬화 (Flower 표준 방식)
- **BatchNorm 주의.** FedAvg로 BN의 running mean/var까지 평균하면 클라이언트 간 입력 분포가 다를 때(강재 vs 알루미늄) 글로벌 모델 성능이 흔들릴 수 있다. FedBN(BN을 로컬에 남기는 방식)이 알려진 처방이지만, 우리는 글로벌 모델 하나를 글로벌 평가셋으로 채점하는 설계라 로컬 BN을 남길 수 없다. 기본은 BN 포함 전체 평균으로 가되, 이 선택과 근거를 논문에 한 문장으로 명시한다. 결과가 크게 흔들리면 BN 통계만 서버 재추정(글로벌 평가셋의 train 부분으로 forward만 수행)하는 보정을 부록 실험으로 둔다

# 4. 텍스트·합성 데이터 파이프라인 (D2·D3·D4)

## 4-1. 문서 파싱

- Docling으로 PDF·HWP 변환본을 구조화(제목 계층, 표)한다. 표는 DataFrame으로 나오므로 허용치 표를 CSV로 바로 뽑는다
- Docling이 실패하는 문서(스캔본, 한글 특수 조판)는 pdfplumber + 수작업 보정으로 처리하고, 어떤 문서를 어느 경로로 처리했는지 목록을 남긴다
- 산출물: `corpus/parse/` 아래 문서별 markdown + 표 CSV

## 4-2. 텍스트 전처리에 대한 교정

계획 수립 중에 "패딩, stopword 등 기본 전처리"가 언급되었는데, 현재 스택에서는 다음이 맞다.

- **불용어 제거·형태소 분석은 하지 않는다.** BERT 계열 이후의 dense 임베딩과 LLM 토크나이저는 원문 그대로를 전제로 학습되어 있어, 불용어를 빼면 오히려 문맥이 깨진다. 이 전처리는 TF-IDF·BM25 시절의 관례다. (BM25를 하이브리드 검색에 보조로 쓸 경우에만 형태소 분석기 기반 토큰화를 그 경로에 한정 적용한다)
- **패딩은 데이터 전처리가 아니라 학습 시 collator가 처리한다.** transformers의 DataCollator가 배치 내 최장 길이에 맞춰 동적 패딩한다. 미리 패딩해 저장하지 않는다
- 실제로 필요한 전처리: 유니코드 정규화(NFC), 공백·개행 정리, 단위 표기 통일(㎜→mm, ℃→°C 등 변환표), 조항 번호 패턴 정규식 추출(`제?\s*(\d+(\.\d+)*)\s*조?항?` 류), 표 셀의 병합 해제

## 4-3. 규칙 기반 판정 골격 생성기 (핵심 자체 구현)

판정 추론 corpus (c)와 이미지-판정문 페어 D4는 같은 엔진에서 나온다. LLM은 문장 표현만 담당하고 수치·논리는 전부 규칙이 만든다.

```
입력 테이블 (허용치 CSV, Docling 추출 + 수기 검수)
  defect_code, thickness_min, thickness_max, quality_level,
  limit_type(길이/직경/비율), limit_value, unit, clause_id, source_doc

생성 절차
 1) 실존 조합 열거: (결함코드 × 두께구간 × 품질수준) 중 표에 행이 있는 것만
 2) 수치 샘플링: 합격 40% / 불합격 40% / 경계(허용치 ±10%) 20%
 3) 골격 JSON 생성:
    {defect_code, size_mm, thickness_mm, quality_level,
     clause_id, limit_value, verdict, margin}
 4) LLM 표현 변주: 골격을 프롬프트에 넣고 "수치와 조항 번호를 바꾸지 말 것"
    제약으로 자연문 생성
 5) 수치 잠금 검증: 생성문에서 정규식으로 수치·조항 번호를 재추출해
    골격과 대조. 불일치는 폐기 (재생성하지 않고 버린다. 통과율 기록)
```

- 경계 사례 20%를 명시적으로 넣는 이유: 무작위 샘플링만 하면 허용치 근처 사례가 희박해져, 모델이 대소 비교를 배우지 못한다
- D4는 2)의 수치 샘플링 대신 실제 이미지 라벨(2-2의 픽셀 크기, 스케일 확인 결과에 따른 mm 환산 또는 가정값)을 입력으로 쓴다는 점만 다르다
- 골격 생성기는 순수 함수로 짜고 단위 테스트(부등식 경계, 조합 누락)를 붙인다. 이 코드가 틀리면 corpus 1만 건이 통째로 오염된다

## 4-4. LLM 생성: 서빙과 모델

- **서빙: vLLM으로 로컬 OpenAI 호환 서버를 띄우고, 생성 스크립트는 openai 클라이언트로 호출한다.** 이렇게 하면 생성 백엔드를 바꿔도(다른 모델, 다른 서버) 스크립트가 그대로다. 배치 처리량도 HuggingFace generate 대비 수 배 이상 나온다. 현재 합성 데이터 생성의 사실상 표준 구성이다
- **생성 모델: 오픈 가중치 모델을 로컬에서 돌린다.** Qwen2.5-32B/72B-Instruct급이 후보. 상용 API 출력으로 타 모델을 학습시키는 것을 약관으로 금지하는 벤더가 있어, 오픈 모델 로컬 생성이 라이선스가 깨끗하고 논문에 "생성 모델 명시"가 가능하다
- **검증 모델은 생성 모델과 다른 계열로 둔다** (예: 생성 Qwen, 검증 Llama-3.x). 자기검증 금지 원칙의 구현이다
- 프레임워크: (b) QA는 자체 프롬프트 스크립트가 기본, Docling-SDG는 W2 표본 100건 검토 후 채택 여부 결정(기존 논의 유지). distilabel(Argilla)도 파이프라인 관리가 필요해지면 대안이지만, 우리 규모(3만 건)에서는 jsonl 스크립트로 충분하다

선행 사례: 도메인 특화 LLM 구축에서 "문서 파싱 → 구절 → LLM 질문 생성 → LLM 심판 필터"가 표준 흐름으로 자리 잡았고(IBM Granite의 Docling 기반 합성 QA, Red Hat SDG Hub 등), 우리 (b)가 정확히 이 형태다. (c)처럼 수치 추론이 걸린 데이터는 규칙 골격 + 표현 변주라는 hybrid가 관례이며, 수학·표 추론 합성 데이터 연구들이 같은 이유(수치 환각 방지)로 이 구조를 쓴다.

# 5. RAG 구현 (분리형 판정부)

## 5-1. 설계의 성격을 먼저 분명히

우리 검색은 자연어 유사도 검색이 아니라 **메타데이터 필터가 1차, 벡터 유사도는 보조**다. 질의가 구조화 키 {결함 코드, 크기, 두께, 품질 수준}이므로, 조항 청크의 메타데이터(결함 코드, 두께 범위, 품질 수준)와의 정확 매칭·범위 매칭으로 후보를 좁힌 뒤, 후보가 복수일 때만 dense 유사도로 top-3을 정렬한다. 사실상 구조화 lookup에 가깝고, 그래서 조항 top-1 정확도가 높게 나와야 정상이며 낮으면 색인 구축 오류를 먼저 의심한다.

## 5-2. 청크 스키마

```json
{
  "chunk_id": "IACS47-3.2.1",
  "doc": "IACS Rec.47",
  "clause_id": "3.2.1",
  "defect_codes": ["2011", "2012"],
  "thickness_min": 8, "thickness_max": 25,
  "quality_levels": ["B", "C"],
  "text": "...조항 재서술 또는 무료 공개 원문...",
  "source_page": 14
}
```

- 청킹은 Docling의 제목 계층으로 조항 경계를 잡는다. 고정 길이 분할 금지 (총괄 보고서 7장 유지)
- 메타데이터 필드는 골격 생성기의 허용치 CSV와 같은 소스에서 나온다. 두 곳이 어긋나면 판정 정합성 지표가 무의미해지므로, 허용치 CSV를 단일 소스로 두고 청크 메타데이터를 그로부터 생성한다

## 5-3. 임베딩·벡터 저장

| 항목 | 채택 | 대안 | 판단 근거 |
|---|---|---|---|
| 임베딩 | BGE-M3 | KURE-v1 (BGE-M3 한국어 파인튜닝), multilingual-e5-large, Qwen3-Embedding | BGE-M3는 MIT 라이선스에 dense+sparse 동시 지원, 한국어 벤치마크 상위. KURE-v1은 한국어 실사용 보고가 좋으나 dense 전용. 최종 선택은 자체 검증(아래)으로 |
| 벡터 저장 | FAISS (IndexFlatIP) 또는 Chroma | Qdrant, Milvus, pgvector | 청크가 수백~수천 개 규모라 flat 인덱스 전수 검색으로 충분. 서버형 벡터 DB는 과잉이다. 메타데이터 필터가 필요하므로 Chroma(필터 내장)가 코드가 짧고, FAISS면 필터를 pandas로 선행하면 된다 |
| 하이브리드 | 선택 | rank_bm25 | 구조화 질의라 필요성이 낮다. 임베딩 검증에서 dense 단독 top-1이 기준 미달일 때만 추가 |

임베딩 모델 선택 절차: 정답 조항 목록에서 질의 100건(결함코드+두께+품질수준 → 정답 청크)을 만들어 후보 모델별 top-1/top-3을 직접 잰다. 벤치마크 순위가 아니라 우리 문서에서의 성능으로 정한다. 임베딩은 재학습하지 않고 고정한다.

## 5-4. 판정부 파이프라인

```
검출 결과 JSON → 질의 키 구성 → 메타 필터 → (복수 시) dense top-3
 → 프롬프트: [검출 결과 + 검색 조항 3건] → LLM(배경지식 학습본, greedy)
 → 판정문 JSON 출력 → 채점기
```

- 프롬프트 템플릿은 파일로 고정하고 스냅샷 해시에 포함한다
- 검색 결과가 0건이면 "해당 조항 없음"을 출력하도록 프롬프트에 명시한다 (환각으로 채우는 것을 방지)

# 6. 미세조정 구현

## 6-1. 스택

| 용도 | 채택 | 대안 | 트렌드 비고 |
|---|---|---|---|
| LLM QLoRA | transformers + PEFT + bitsandbytes + TRL SFTTrainer | LLaMA-Factory (YAML 설정 기반, 재현 관리 편함), Axolotl | TRL 직접 사용이 통제력이 가장 높다. LLaMA-Factory는 팀원 진입 장벽을 낮추는 장점이 있어 병용 가능 |
| VLM QLoRA | transformers (Qwen2.5-VL 공식 예제 경로) + PEFT | Unsloth FastVisionModel (24GB 제약 시), LLaMA-Factory VLM 지원 | Unsloth 도입 조건은 기존 논의 유지: GPU 확정 후 판단, 쓰면 언어모델 학습 세 곳 전부 동일 적용 |
| 추론(평가 시) | vLLM (LoRA 어댑터 로드 지원) | transformers generate | 평가 2,000건×5칸 추론 비용을 vLLM이 크게 줄인다 |

## 6-2. 하이퍼파라미터

값은 파일럿 전 초기값이며, 파일럿 후 고정한다는 조건을 달아 둔다. 확정값은 configs/에만 존재하고 문서에는 "configs 참조"로 링크한다 (문서와 코드의 이중 관리 방지).

| 단계 | 대상 | r / alpha | LR | 유효 배치 | epoch | 조기 종료 |
|---|---|---|---|---|---|---|
| (선택) 추가 사전학습 | LLM·VLM 언어부 | 128 / 256 | 1e-5 | 64 | 1 | 없음 |
| 지시 학습 (QA) | 〃 | 16 / 32 | 2e-4 | 64 (grad accum) | 3 | 없음 |
| 추론 학습 (판정) | 〃 | 16 / 32 | 1e-4 | 64 | 3 | 없음 |
| 통합형 본학습 (D4) | VLM | 16 / 32 | 1e-4 | 32 | 3 | 없음 |

- **조기 종료는 전 단계에서 쓰지 않는다.** 이유는 검출과 같다: 다섯 칸 학습량 등가(R×E=N)가 논문의 공정성 주장인데, 조기 종료는 칸마다 다른 학습량을 만든다. val loss는 로깅만 하고 개입하지 않는다
- 대상 레이어: attention q,k,v,o + MLP (PEFT target_modules="all-linear"가 최근 관례). 비전 인코더는 동결(통합형 어댑터 크기 축소, 통신량 이점)
- max_seq_length: QA 1,024 / 추론·판정문 2,048. 초과 샘플은 자르지 말고 폐기 후 건수 보고
- 패킹(sample packing)은 쓰지 않는다. 속도 이점보다 "노출 횟수 등가" 계산의 단순함을 택한다

## 6-3. 좌표계 문제 (v2 보고서 교정 사항)

총괄 보고서는 bbox를 0~1000 정규화로 통일한다고 썼는데, 구현 관점에서 한 겹 더 정확히 해야 한다. **Qwen2-VL은 0~1000 정규화 좌표로 학습되었지만 Qwen2.5-VL은 리사이즈된 이미지의 절대 픽셀 좌표를 쓴다.** 모델 네이티브 좌표계와 다른 형식으로 파인튜닝하면 사전학습된 grounding 능력을 버리고 새로 배우는 셈이 되어 손해다.

- 구현 원칙: **학습 타깃 좌표는 채택 모델의 네이티브 형식을 따른다.** 채택 모델 확정 시 공식 문서로 형식을 재확인하고 데이터 생성 코드에 반영한다
- 데이터 파일에는 원본 픽셀 좌표를 저장하고, 학습용 변환·채점용 역변환을 각각 함수로 둔다
- 채점은 원본 이미지 좌표계로 역변환한 뒤 IoU를 계산한다. 선행 연구의 0.055→0.938 사례는 "좌표계 불일치가 지표를 붕괴시킨다"는 교훈으로, 정확한 처방은 정규화 자체가 아니라 좌표계 일치다

# 7. 연합학습 구현 (Flower)

## 7-1. Flower 현재 구조

Flower 1.x의 현행 API는 `flwr new`로 프로젝트를 생성하고 ServerApp·ClientApp 두 진입점을 정의한 뒤 `flwr run`으로 실행하는 구조다. 설정(라운드 수, 로컬 epoch, 배치)은 pyproject.toml의 run-config에 두고 실행 시 override할 수 있다. 시뮬레이션은 Ray 백엔드가 클라이언트 프로세스를 관리하며, 클라이언트당 GPU 지분(예: num_gpus=0.33)을 지정할 수 있다. FedAvg를 포함한 표준 전략(FedProx, FedAvgM 등)이 내장되어 있다.

우리 실행 형태는 **1 GPU 위의 시뮬레이션**이다. 3클라이언트가 물리적으로 분산되어 있지 않으므로, 논문에는 "시뮬레이션 환경이며 통신량은 교환 객체 크기 실측 × 라운드 수로 산출"임을 명시한다. VLM처럼 클라이언트 하나가 GPU를 다 쓰는 경우 클라이언트를 순차 실행(동시성 1)으로 돌리면 된다. 시뮬레이션이라 가능한 방식이다.

대안 프레임워크: NVFlare(산업·보안 기능 강함, 무거움), FedML, OpenFL. 연구용 표준은 Flower로 수렴한 상태고, LLM 연합 파인튜닝 벤치마크(FlowerTune)도 Flower 생태계에 있다. 바꿀 이유가 없다.

## 7-2. 검출 FL (분리·연합)

```python
# Client 측 핵심 (개념 코드)
get_parameters: model.state_dict() → [ndarray]   # BN 통계 포함
fit: set_parameters → E epoch 로컬 학습 → get_parameters, len(train_set) 반환
# Server 측
strategy = FedAvg(가중 = 클라이언트 표본 수)      # C1:C2:C3 ≈ 32k:16k:8k
```

- Ultralytics 결합 지점: trainer를 epoch 단위로 호출할 수 있도록 래핑하거나, model.model(내부 nn.Module)의 state_dict를 직접 다룬다. Ultralytics의 자체 저장·재개 로직과 Flower의 파라미터 주입이 충돌하지 않게, 학습 루프를 커스텀 트레이너로 한 겹 감싼다
- R×E=N: N=100 기준 R=50·E=2를 기본으로 하고 파일럿에서 확정. optimizer 상태(momentum)는 라운드마다 리셋됨을 인지하고 명시 (FedAvg 표준 동작)

## 7-3. VLM FL (통합·연합)

- 교환 단위: PEFT의 `get_peft_model_state_dict()` 결과(LoRA A·B 행렬)만. 기본 모델은 각 클라이언트에 사전 배포된 동일 체크포인트
- 집계: 행렬별 가중 평균 (avg(A), avg(B)). avg(B)·avg(A) ≠ avg(B·A) 문제는 논문 명시, 여유 시 갱신량(ΔW) 평균 방식(FLoRA 계열)을 부록 비교
- 라운드 흐름: 서버가 어댑터 배포 → 클라이언트가 기본 모델에 로드 후 로컬 학습 → 어댑터만 반환. 병합(merge)은 라운드 중에는 하지 않고, 최종 라운드 후 1회 병합해 평가용 체크포인트를 만든다
- 통신량 실측: 직렬화된 ndarray 바이트 수를 라운드마다 로깅. 어댑터(r=16, 언어부만)면 라운드당 수십 MB, 검출 전체 가중치(YOLOv8n fp32 기준 약 12MB, fp16 직렬화 시 절반)와의 대비가 결과 표에 들어간다

선행 사례: LoRA 어댑터만 FedAvg로 교환하는 연합 지시 튜닝(FedIT 계열)이 확립된 패턴이고, 4bit 고정 기본 모델 + 어댑터 교환 구성의 구현 보고도 다수다. 우리 통합·연합 칸은 이 패턴의 VLM 적용이다.

## 7-4. 라운드 관리

- 라운드마다: 글로벌 파라미터 저장(마일스톤 라운드만 보존, 아래 10-2), **`val` 지표**를
  서버 사이드 evaluate 콜백에서 산출해 MLflow에 round=step으로 로깅
- **`val`은 학습 풀의 10%**(묶음 단위·층화, 로깅 전용)이며 **글로벌 평가셋이 아니다.**
  글로벌 평가셋은 전 실험을 통틀어 **최종 채점 1회만** 접근한다. 조기 종료를 쓰지 않고
  last를 채점하므로 라운드별 곡선에는 선택압이 없다 — 그럼에도 두 집합을 분리해 두는 것은
  "평가셋이 학습·선택에 영향을 주지 않는다"는 주장을 문구 수준에서까지 방어하기 위해서다
- 클라이언트 로컬 체크포인트는 저장하지 않는다 (시드+분할+설정으로 재현 가능)
- **`accept_failures=False`.** Flower FedAvg 기본값(`True`)은 클라이언트가 라운드 중 실패해도
  나머지로 집계를 진행해, 실효 학습량이 줄어든 사실이 지표에 남지 않는다. `R × E = N` 등가가
  조용히 깨지는 경로이므로 금지한다. 실패 시 라운드를 중단하고 사람이 개입한다
- **클라이언트 × 라운드 회계 매트릭스**를 정식 산출물로 남긴다. 라운드별 각 클라이언트의
  참여 여부·로컬 스텝 수·표본 수를 기록하고 종료 시 `R × E = N`을 실측 검증한다.
  총 갱신 횟수는 이 실측치를 논문에 싣는다
- 실패 복구: 라운드 단위 재시작이 가능하도록 서버가 최신 글로벌 파라미터를 항상 디스크에 남긴다

> 2026-08-17 총괄 정정 (검토 결정 B·E). 개정 전 문구가 "글로벌 평가셋 val 지표"로
> 두 집합을 뭉뚱그려, C·D가 서로 다른 개정안을 전제하는 원인이 되었다.

# 8. 평가 구현

## 8-1. 공통 채점기 원칙

다섯 칸의 출력을 전부 **공통 예측 JSON 스키마로 변환한 뒤 단일 채점기**로 채점한다. 칸마다 채점 코드를 따로 짜면 공정성 주장이 무너진다.

```json
{"image_id": "...", "defects": [{"iso_code": "2011", "bbox_px": [x1,y1,x2,y2],
  "size_mm": 2.1}], "verdict": "합격", "cited_clauses": ["IACS47-3.2.1"],
  "parse_ok": true}
```

- 분리형: 검출 출력 + 판정부 출력을 이 스키마로 조립
- 통합형: 생성 텍스트를 json.loads + pydantic으로 파싱. 실패 시 parse_ok=false로 기록하고 해당 이미지의 검출·위치 지표는 오답 처리. 재시도·재프롬프트 없음 (greedy 1회 원칙)

## 8-2. 지표별 산출 방법과 자동화 수준

| 지표 | 산출 | 자동화 수준 |
|---|---|---|
| Macro-F1, 클래스별 P/R, 혼동행렬 | 이미지 수준 결함 유무·종류로 산출 (sklearn) | 완전 자동 |
| 결함 recall (놓침 비율) | 결함 이미지 중 해당 결함을 하나라도 잡은 비율 | 완전 자동 |
| mAP@0.5, 0.5:0.95 | COCO 형식 변환 후 pycocotools. 다섯 칸 동일 채점기 | 완전 자동 |
| Class-Jaccard | 판정문 언급 결함 집합 ↔ 라벨 집합의 Jaccard | 완전 자동 (JSON 필드 기준) |
| BBox-IoU | 예측 bbox ↔ 라벨 bbox, 좌표 역변환 후 | 완전 자동 |
| 조항 검색 top-1/3 | 검색 로그 ↔ 정답 조항 CSV 대조 | 완전 자동 (정답 목록 확정 후) |
| 인용 일치율 | cited_clauses ↔ 정답 조항 | 완전 자동 |
| 판정 정합성 | 인용 조항의 허용치 CSV 값 + 크기 값으로 부등식 재계산 ↔ verdict | 규칙 기반 자동 (허용치 CSV가 정답 소스) |
| 무근거 인용률 | 1차: 조항 ID가 색인에 실존하는가 (자동). 2차: 실존하지만 무관한 인용은 정답 매핑 대조 (자동) + 경계 사례만 사람 판정 | 자동 + 표본 검수 |
| latency, VRAM | warmup 10회 후 100장 median, batch=1, 동일 GPU, torch.cuda.max_memory_allocated | 완전 자동 (측정 스크립트 고정) |
| 통신량 | 직렬화 바이트 실측 × 라운드 | 완전 자동 |

## 8-3. 사람이 직접 하는 일 (전체 목록)

1. 정답 조항 목록 확정 (결함×두께×품질수준 → 조항). 전문가 확인 필수, 이후 전 지표의 기준이 됨
2. corpus·페어 표본 2~3% 검수 (검증 3단계의 마지막)
3. 무근거 인용 중 "실존하나 무관" 경계 사례 판정 (표본)
4. pHash 임계·증강 설정 등 파일럿 결과 눈 확인
5. 판정문 자연스러움 소표본 평가 (보조 지표, 5점 척도, 논문에는 부록)

이 다섯 개 외에는 전부 스크립트다. 사람 검수 결과도 시트로 남겨 통과율을 논문에 쓴다.

# 9. 베이스라인과 해석 기준선

절대 목표치를 걸기보다 "이 수치면 이렇게 해석한다"는 기준선을 사전에 합의해 둔다. 사후 합리화 방지가 목적이다.

| 항목 | 참조점 | 해석 기준선 |
|---|---|---|
| 분리·중앙 검출 | AI허브 참조 모델(YOLOv5x-seg) 공개 성능치. 데이터 설명서에서 확인, 체급 차이(88M vs 3.2M) 명시 | Macro-F1 0.85 이상이면 파이프라인 정상. 미달 시 결과 해석 전에 라벨·분할 오류 먼저 점검 |
| 분리형 회복률 | non-IID FedAvg 문헌에서 통상 85~95% 회복 보고 | 90% 이상 강한 결과, 80~90% 방어 가능, 80% 미만이면 non-IID 심화 효과로 해석하고 클라이언트별 분해 제시 |
| 통합형 유지율 | 어댑터 FedAvg 문헌상 중앙 대비 소폭 하락이 일반적 | 90% 이상이면 통합형도 연합 가능 주장 성립 |
| 통합형 절대 성능 | 선행 연구(WeldLLM)의 Class-Jaccard·BBox-IoU 보고치. 데이터가 달라 직접 비교 아닌 참조점, 제로샷 실측이 하한선 | 제로샷 대비 유의한 향상이 있으면 학습 효과 성립. 분리형에 밀려도 그 자체가 RQ2의 답 |
| RQ3 편익 | 없음 (자체 비교) | C3의 결함 recall이 로컬 대비 +5%p 이상이면 참여 편익 주장 성립 |
| 조항 top-1 | 없음 (구조화 lookup) | 95% 이상이 정상. 미달 시 색인·메타데이터 구축 오류부터 의심 |
| 판정 정합성 | 없음 | 95% 이상 기대. 미달분은 오류 유형 분해(조항 오검색 vs 대소 비교 실패)로 보고 |

미달이 곧 실패가 아니라는 원칙을 공유한다. 다섯 칸 비교가 성립하는 한, 어느 칸이 어디서 무너지는지 자체가 결과다.

# 10. 실험·모델 관리

## 10-1. MLflow

- 로컬 tracking 서버(sqlite backend + 파일 artifact store)로 충분하다. W&B는 편하지만 기본이 외부 클라우드 로깅이라 "데이터 비반출" 서사와 어긋나 보일 수 있고, 로컬 서버 모드를 쓸 거면 MLflow 대비 이점이 없다
- run 구조: experiment = "weld-fl", run 명명 `{cell}_{seed}_{yymmdd}` (예: `sep_fed_s0_260910`)
- 필수 로깅: config YAML 전체(artifact), git commit hash, manifest·스냅샷 sha256, 지표(FL은 round를 step으로), 학습 곡선, 최종 결과 JSON
- Flower 결합: 서버 evaluate 콜백 안에서 mlflow.log_metrics(round=step) 호출. 클라이언트 쪽은 로깅하지 않는다 (서버 시점 지표로 통일)
- 결과 표(8-6)는 MLflow에서 스크립트로 추출해 생성한다. 손으로 옮겨 적지 않는다

## 10-2. 체크포인트 규칙

| 항목 | 규칙 |
|---|---|
| 명명 | `{cell}_{stage}_{round|epoch}_{seed}.pt` |
| 보존 | 로컬·중앙 칸: last만. FL 칸: 최종 + 마일스톤 라운드(25%, 50%, 75%) 글로벌만 |
| 동반 저장 | 같은 폴더에 config.yaml, 지표 JSON, 생성 코드 commit hash |
| 공통 출발점 | 배경지식 학습 완료 체크포인트(병합본)는 별도 디렉터리에 동결, 해시 기록. 다섯 칸이 전부 이 해시를 로깅해 동일 출발 증명 |
| 용량 추정 | VLM 3B fp16 병합본 약 6~7GB × (출발점 1 + 통합 칸 산출물), 검출 모델은 수십 MB라 무시 가능. 로컬 디스크 수백 GB면 충분, 정리 스크립트로 마일스톤 외 자동 삭제 |

## 10-3. 연합학습 특유의 관리 사항

- 글로벌 모델만 관리 대상이다. 클라이언트 로컬 상태는 (시드, manifest, config)로 재현되므로 저장하지 않는다
- 라운드별 지표 CSV(라운드, 손실, F1, 통신 바이트)를 MLflow와 별도로 남겨 그림 생성에 직접 쓴다
- 어댑터 집계 직전·직후 파라미터의 norm을 로깅한다. 집계 버그(순서 뒤섞임, dtype 불일치)를 조기에 잡는 저비용 안전장치다

## 10-4. 재현성 최종 점검 목록

논문 제출 전에 다음을 새 환경에서 1회 재실행해 확인한다: manifest 재생성 일치(해시 대조), 분리·중앙 1시드 재학습 지표 오차 범위, 채점기 재실행 결과 일치. 전부 스크립트 하나(`make reproduce-check`)로 묶는다.
